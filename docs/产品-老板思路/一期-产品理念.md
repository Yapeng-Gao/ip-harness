## 1. 卖什么

卖的是一支**已经组织好、有管理、可协同**的研发创新团队——上手即用。  
不是散装大模型能力，不是「一键生成」黑箱外包。

用户（中小企业研发、企业 IP、代理所代理人）从「一个人扛」变成「带团队干」；AI 熟悉度不一，**交互默认按最不懂 AI 的那位设计**。

## 2. 组织形状（拟人化）

| 现实类比 | 产品 |
|---|---|
| 公司 | 新质数研发创新团队 |
| **八个部门** | **老板八节点**（①～⑧） |
| 部门内多名**专家** | 各节点内的 AI 岗位（编制在产品设计阶段定） |
| 请示汇报 | 专家递方案 + 依据 → 领导拍板 |
| 真人代理师 | **共生武装，不是替代** |

业务逻辑回答：这个部门**办什么事**。  
产品设计回答：这个部门**有哪些专家、怎么协作**。  
本文件回答：全公司**按什么原则当领导、用员工**。

**系统门禁（已钉，对齐老板「一套团队」）：**  
→ **一套系统；任何用户都能使用所有部门，不做按用户身份锁部门。**  
→ **进门大厅：前台接待 + 八部门都可见**；前台是引导不是唯一闸门。  
详见 [`一期-产品逻辑/00-用户与系统.md`](一期-产品逻辑/00-用户与系统.md)、[`01-接待与分诊.md`](一期-产品逻辑/01-接待与分诊.md)。

## 3. 「领导」是谁

**领导 = 当前用户**：此刻正在用系统的人；各部门专家一律向 TA 汇报、由 TA 点头或退回。  
不是职级头衔，不是按节点写死的「发明人岗/IP 岗」；换人操作，领导就换人。

惯用上谁更常来哪一站（研发常来交底、代理常来申请）只影响**谁更容易成为当前用户**，不改变汇报规则。

理念红线：**别让 AI 偷拍板**；该汇报必须汇报到当前用户。  
门禁：谁都可以进各部门（见上）。

---

## 4. 企业与代理（同一系统里的协作）

对齐代理所册：客户自助 + 代理师前置；专业站代理人往往更会用，企业要能打开同一部门获得**认知与判断**（卖方市场下尤其需要）。

| | 说明 |
|---|---|
| 系统 | **同一套**，部门**不限身份** |
| 惯用 | ②④ 企业常主操；③⑤⑥ 代理常主操——服务设计参考四方表 |
| 企业 | 可进专业站看过程/选项/依据，形成判断，不被迫改行当代理 |
| 代理 | 可进成稿等部门诊断、陪同；主笔申请仍常在⑤ |
| 共生 | 武装代理，也武装企业知情力；不替代代理师签字位置 |

## 5. 机制红线（当前认的；编制中可打磨）

| 红线 | 一句话 |
|---|---|
| 依据链 | 结论要能签字：来源 / 推演 / 对比；缺链不上关键交付 |
| 授权 | 有的事专家自决，关键事必须请示；不事事打断，也不黑箱闷头 |
| 质检与检查点 | 有把关、节奏合适 |
| 带教 | 脚手架，熟了淡出；不是价值承重墙 |
| 沉淀 | 重判断数据与默契，不重操作考勤 |
| 交互语言 | 专家 / 部门 / 请示；不默认「模型 / Prompt / Agent」对外话术 |

符合性检查可**试用** skill 里的 14 问（扫编制稿，不扫业务文）；条目本身允许在部门设计与试点里改、删、加——**验证优先于维持 skill 原貌**。
