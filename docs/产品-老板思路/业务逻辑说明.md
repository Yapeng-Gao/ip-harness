# 专利挖掘（patent-dig）业务逻辑说明

> 面向工程化改造与部署的工程师。本文基于当前代码事实整理，描述产品定位、端到端流程、领域模型、各模块规则、外部依赖与鉴权边界。  
> 代码根目录：
> - 前端：`patent-dig-front-master-…`
> - 后端：`patent-dig-backend-master-…`
> - API 前缀：`http://<host>:8080/api`

---

## 1. 产品定位与使用者

### 1.1 做什么

**创新挖掘 / Patent Dig** 是一套「企业研发资料 → 可复核专利布局建议与分析报告」的 AI 辅助工作台。

- **输入**：企业研发资料（设计/需求/可行性/技术方案等），产品侧刻意避免把输入称作「专利交底书」。
- **输出**：
  - 结构化创新点（含去向建议）
  - 现有技术检索证据与风险矩阵
  - 申请布局 / 组合布局建议
  - 双口径分析报告（研发诊断稿 / 代理师交付稿），可导出 Word/PDF

### 1.2 不做什么

- 不是立案系统、不是权利要求书自动定稿系统。
- 报告与布局均为 **AI 初稿**，须专利代理师复核；报告声明中明确：不替代研发发明与代理师撰写。

### 1.3 主要使用者

| 角色 | 典型动作 |
|------|----------|
| 专利代理师 / IP | 主操：确认证据、布局、导出「代理师交付稿」 |
| 企业研发 | 提供资料；阅读「研发诊断稿」（补料任务、证据进度） |
| 本地联调 / 演示 | `AUTH_MOCK=true` 任意账号进入前端 |

## 2. 端到端主路径（Happy Path）

前端四步：**资料 → 创新点 → 布局 → 报告**。  
步骤解锁按 **结果是否存在**，不是严格的 `ProjectStatus` 锁步；报告在「已有创新点」时即可进入（布局可缺省）。

```
登录
  → 创建项目（上限 20）
  → 上传/粘贴研发资料，设置归属（自有/公开/待确认）
  → 解析资料（抽文本 + LLM 结构化）
  → （可选）生成企业洞察 / 挖掘 intake
  → 提炼创新点（旧创新点与布局会软删重建）
  → 人工确认/编辑/合并/排除；对可布局去向自动检索对比文件
  → （可选）深挖：创造性分析、权利要求草稿
  → 生成布局建议（质量闸门）→ 确认布局 / 组合布局
  → 生成报告（研发 or 代理师口径）→ 编辑块 → 导出 Word/PDF
```

### 2.1 分步对应关系

| 步骤 | 用户动作 | 后端主要效果 |
|------|----------|--------------|
| 登录 | Mock 或用户中心 | 仅 Next 侧 Cookie；**不传给 Spring** |
| 建项 | 首页新建 | `POST /projects` → `MATERIAL_PENDING` |
| 资料 | 上传文件 / 粘贴文本 | 抽文本（Tika / Qwen-Doc）；解析后 → `INNOVATION_PENDING` |
| 洞察 | 可选：企业洞察 | `enterprise-insight/generate` |
| 创新点 | 提炼 / 确认 / 合并 | LLM 抽取；可布局去向异步检索；状态保持/更新为 `INNOVATION_PENDING` |
| 布局 | 生成并确认 | 仅 `included` + 可布局去向；→ `LAYOUT_PENDING` |
| 报告 | 生成并导出 | 归档旧报告；→ `REPORT_PENDING`；导出带质量闸门 |

说明：枚举里有 `COMPLETED`（UI 筛选项「已完成」），但当前服务代码中 **未发现写入该状态**。

## 3. 领域模型

### 3.1 核心实体关系

```
Project
  ├─ * ProjectMaterial
  │     └─ * MaterialParseResult（其中一条 isCurrent）
  ├─ 0..1 EnterpriseInsight
  ├─ * Innovation
  │     ├─ * PriorArtEvidence
  │     ├─ * LayoutAdvice
  │     ├─ 0..* InventiveStepAnalysis / ClaimDraft（深挖）
  │     └─ Discovery 候选（漏挖）
  ├─ 0..1 PortfolioLayoutPlan（组合布局）
  │     └─ * PortfolioCase / Relation / CaseInnovation
  └─ * Report（当前一份 GENERATED，旧份 ARCHIVED）
        ├─ * ReportBlock
        └─ * ReportExportRecord
```

### 3.2 关键字段（业务含义）

| 实体 | 关键字段 |
|------|----------|
| Project | `name`、`field`、`status`、`innovationCount`；软删 `deleteFlag` |
| ProjectMaterial | `sourceType` FILE/TEXT；`parseStatus`；`ownershipBucket`；`extractEngine`；`rawText` |
| MaterialParseResult | 大纲/摘要；`qualityStatus`；`materialRole`；归属判断 |
| Innovation | 问题-方案-效果三元组；实施例；关键特征；`disposition`；`noveltyRisk`；`included`；特征矩阵 |
| PriorArtEvidence | 公开号/标题/摘要/语义分；`verified`（**仅人工**）；`source` |
| LayoutAdvice | 保护定位/申请类型/策略/优先级/四方向；`status` |
| Report | `audience` ATTORNEY / R_AND_D；块内容；导出记录 |

## 4. 项目状态机

### 4.1 状态码与界面文案

| 代码 | UI 文案 | 谁写入 |
|------|---------|--------|
| `MATERIAL_PENDING` | 待研发资料 | 新建默认 |
| `INNOVATION_PENDING` | 待创新点 | 解析完成、提炼创新点后 |
| `LAYOUT_PENDING` | 待布局建议 | 生成布局后 |
| `REPORT_PENDING` | 待报告 | 生成报告后 |
| `COMPLETED` | 已完成 | **仅筛选展示，业务未写入** |

### 4.2 与前端步骤条的关系

步骤「完成」判定（独立于 status）：

1. 资料完成：至少一份材料 `PARSED`
2. 创新点完成：至少一条创新点
3. 布局完成：至少一条布局建议
4. 报告完成：存在当前报告  

解锁规则：第 N 步通常依赖前序结果；**报告**在已有创新点时即可进入（可不先做布局）。

**没有正式「锁步门禁」开关**；硬阻塞主要来自质量闸门（模板资料等）。

## 5. 模块详解

### 5.1 研发资料（Workspace）

#### 上传与抽文本

- 支持：txt/md/pdf/doc(x)/xls(x)/ppt(x) 等，单文件 ≤ 32MB。
- PDF：优先 **百炼 Qwen-Doc**（`qwen-doc-turbo`）。
- 数字化 Office/纯文本：默认可先走本地 **Tika**；内容过薄或策略要求时再升到 Qwen-Doc。
- 附图：可选百炼 Vision，写入 `【附图N｜…】` 块。

抽取状态示意：`LOCAL` / `QWEN` / `UPGRADING` / `UPGRADE_FAILED` / 粘贴跳过。

#### 解析（LLM）

`AiDraftService.parseMaterial`：结构化摘要、充分度、资料角色、归属判断（若为待确认）。

**资料角色 `materialRole`：**

| 代码 | 含义 |
|------|------|
| COMPANY_INTRO | 企业介绍 |
| TECH_RD | 研发技术 |
| BUSINESS_PLAN | 经营规划 |
| MIXED | 混合资料 |

**归属 `ownershipBucket`：**

| 代码 | UI |
|------|-----|
| OWN | 自有研发资料 |
| PUBLIC | 公开资料 |
| PENDING | 待确认 |

**解析状态：** `UNPARSED` → `PARSING` → `PARSED` | `FAILED`。

#### 企业洞察（可选）

生成企业画像、技术树、研发问题、mining intake 等 JSON，供后续提炼与布局引用。

---

### 5.2 创新点（Innovations）

#### 提炼

前提：存在当前解析结果。  
效果：软删旧创新点 + 关联布局，并使深挖分析失效；若无企业洞察会先补生成。  
LLM 抽取后默认写入去向；仅 `APPLY_NOW` / `NEED_DETAIL` 默认 `included=true`（可参与布局）。

提炼后异步：优先对可布局去向做现有技术检索；可触发漏挖发现。

#### 去向 `disposition`

| 代码 | UI 文案 | 可否进布局生成 |
|------|---------|----------------|
| APPLY_NOW | 建议申请 | 是 |
| NEED_DETAIL | 补充后可申请 | 是 |
| RESERVE | 技术储备 | 否 |
| TRADE_SECRET | 商业秘密 | 否 |
| ABANDON | 放弃/不宜专利 | 否 |

#### 创新点状态

`PENDING` / `CONFIRMED` / `EDITED` / `EXCLUDED`。

#### 人工操作

新增、编辑、确认、排除、复制、删除、合并；合并建议（词面 + LLM）。

#### 启发式降级（后端）

企业介绍向、机制薄弱、类 CRUD 看板等内容，可能被强制降为 `RESERVE` / `ABANDON` / `NEED_DETAIL`，避免「空壳创新点」进入申请路径。

---

### 5.3 现有技术检索与证据（Prior Art）

#### 检索流水线（概要）

1. 提炼可权利要求化的关键特征  
2. 软删该创新点旧证据  
3. **incoPat**：语义 + 关键词召回、合并排序  
4. 命中过少时 **知产宝 MCP** 关键词补召回  
5. 知产宝补全著录项；同族折叠；跨创新点公开号去重偏好  
6. 特征就绪则 LLM 写风险矩阵 / 创造性简述；否则可只落候选  
7. 触发深挖刷新  

#### 关键规则

- **`verified` 仅人工勾选**，不会因相似度高而自动核验。  
- **分析池**：已核验 ∪ 语义分 ≥ 门槛（默认约 0.78），否则兜底取 Top。  
- **正式报告 D1 口径**：原则上只用已核验证据；无核验则表述为待核验，而非假装有 D1。  
- 证据分层文案：检索候选 / 已关联 / 已确认 / 正式 D1 / 矩阵就绪 —— 避免只说「对比文件 N 件」。

#### 集成状态

`READY` / `NOT_CONFIGURED` / `DISABLED`（前端展示 incoPat / 知产宝是否可用）。

---

### 5.4 布局建议（Layouts）

#### 生成闸门

- 至少一个 `included` 且去向为 `APPLY_NOW` 或 `NEED_DETAIL` 的创新点。  
- 通过 **质量闸门**（见第 6 节）；模板资料硬阻断。  
- 若已有布局，需确认覆盖。  
- 若全部为储备/秘密/放弃 → 无法生成布局。

#### 单条布局字段（常用）

| 字段 | 取值与中文 |
|------|------------|
| 保护定位 | CORE 核心 / PERIPHERAL 外围 / DEFENSIVE 防御 / RESERVE 储备 |
| 申请类型 | INVENTION 发明 / UTILITY 实用新型 / MIXED / DESIGN / NO_APPLY |
| 申请策略 | IMMEDIATE 可尽快 / SUPPLEMENT_FIRST 先补材料 / DOMESTIC / PCT / DEFER |
| 优先级 | P1–P4 |
| 四方向 | 替代方案 / 新用途 / 系统 / 制造工艺等 |
| 状态 | PENDING 待确认 / EDITED 已编辑 / CONFIRMED 已确认 |

#### 组合布局（Portfolio）

多案组合：案件、关系（PARENT / DEPENDENCY / OVERLAP / ALTERNATIVE / DIVISIONAL 等）、立案顺序。  
有组合布局时，生成报告通常要求组合亦已确认（或走 force 覆盖）。

---

### 5.5 报告（Report）

#### 双口径

| 代码 | 含义 |
|------|------|
| `ATTORNEY` | 代理师交付稿（代理师口径） |
| `R_AND_D` | 研发诊断稿（研发人员口径） |

词表与叙述侧重点由 `ReportLexicon` 等按口径改写：研发稿更强调补料与进度；代理师稿更强调交付与检索结论表述。

#### 生成规则

- **无布局也可生成**分析型报告。  
- **有已纳入布局**：通常要求布局全部 CONFIRMED；有组合布局则一并确认（除非 `forceUnconfirmedLayouts`）。  
- 覆盖全部去向；「拟申请」章节依赖布局是否存在。  
- 旧报告归档为 `ARCHIVED`，新报告 `GENERATED`。

#### 章节骨架（代理师口径示意）

执行摘要 → 查新与证据进展 → 去向一览 → 现有技术观察 → 拟申请点 dossier → 暂不申请 → 申请安排 → 路线图 → 行动清单 → 附录（对比文件 / 矩阵 / 漏挖 / 术语 / 声明）

研发口径同骨架，附录与措辞偏向补料任务。

#### 导出

- 格式：WORD（推荐）/ PDF / EXCEL  
- 范围：全文 / 勾选 / P1 / 按创新点 / 按布局等  
- **导出质量闸门**：占位符泄漏、关键表格、交叉引用一致性等；模板资料硬阻断；`NEED_DETAIL` 可通过 UI 确认后 `forceInsufficientMaterial` 放行。

## 6. 质量闸门（Material Quality Gate）

`MaterialQualityGateService` 汇总项目资料充分度：

| Level | 含义 | blockHard |
|-------|------|-----------|
| OK / GOOD | 可继续 | false |
| NEED_DETAIL | 需补材料；布局/导出需 force 确认 | false |
| TEMPLATE | 模板/占位资料 | **true，不可 force** |

模板判定要点：文件名含「模板/样例/示例」等；或填空提示密度高且缺少实质技术正文（需一定字数 + 技术标记）。

接口：`GET /api/projects/{id}/quality-gate`。

## 7. 深挖与漏挖（可选增强）

### 7.1 深挖（Deep Mining）

- 创造性分析（InventiveStepAnalysis）  
- 权利要求草稿（ClaimDraft）  
- 状态：DRAFT / CONFIRMED / STALE（输入变更后标记过期）  
- 证据池依赖已核验或高分对比文件  

### 7.2 漏挖发现（Discovery）

提炼后可异步生成「可能遗漏的创新点」候选；用户可接受 / 忽略 / 合并进正式列表。

|------|------|----------|
| MySQL | `MYSQL_*` | 始终（持久化） |
| Redis | `REDIS_*` | 始终（缓存等） |

| 用户中心 | 前端 `AUTH_*` | 仅关闭 Mock 时前端登录；**后端 API 未校验** |

## 9. 鉴权模型（务必读）

### 9.1 前端

- 无 Cookie `x-access-token`（或过期）→ 跳转 `/login`。  
- `AUTH_MOCK=true`：任意账号密码签发本地 mock token。  
- Mock 关闭：Next BFF 调用户中心 `AUTH_LOGIN_URL` / `AUTH_USER_INFO_URL`。

### 9.2 后端缺口（现状）

- Spring **无**统一 Security / Token 校验。  
- 前端 `services/api.ts` **不**向后端附加登录 Token。  
- 项目列表为全局未删除项目，**非按用户隔离**。  
- `ownerUserId` 等字段存在但未与登录态打通。

**工程含义：** 当前鉴权只挡 Next 页面；能访问 `:8080` 即可调业务 API。上线前必须补后端鉴权与数据隔离。

## 10. 重要业务规则清单

1. 活跃项目上限 **20**。  
2. 普遍软删除（`deleteFlag`），非物理删。  
3. **重新提炼创新点**会作废旧布局与深挖结果。  
4. 仅 `APPLY_NOW` / `NEED_DETAIL` + `included` 可进布局生成。  
5. **TEMPLATE** 资料：布局与导出硬阻断。  
6. **NEED_DETAIL** 资料：软阻断，UI 确认后可 force。  
7. 证据 `verified` ≠ 高相似；正式 D1 口径以已核验为准。  
8. 特征未就绪时，检索可落候选，但可能跳过正式风险/创造性成文。  
9. 无布局可出报告；有布局则默认需确认（或 force）。  
10. 组合布局未确认会挡报告（除非 force）。  
11. 报告生成与导出的质量闸门不完全同一套：导出更严。  
12. 企业介绍 / 机制薄弱等内容可能被降级去向。  
13. 跨创新点公开号去重偏好，避免重复堆证据。  
14. 库内英文枚举码，中文在 UI / `EnumLabels` / 报告词表。  
15. `COMPLETED` 状态未由业务写入。  
16. 无「演示模式 / 正式锁步」产品开关。

## 11. 主要 API 一览
