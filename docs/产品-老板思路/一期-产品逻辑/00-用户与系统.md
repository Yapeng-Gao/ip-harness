# 用户与系统（与老板对齐）

> **文内分层**：本文＝**产品逻辑**通则（案卷/门槛/合格线）。编制与交互见 [产品设计-编制总览](产品设计-编制总览.md)、[交互大纲](交互大纲.md)——**不等于**还在开逻辑大扫。

> **权威对齐**：总纲「AI 团队 + 前置代理师」、代理所册四方协作表、技术册客户侧/代理师侧（能力分布，**非门禁**）。  
> **本期产品钉法**（会话 2026-10-29）：**一套系统；任何用户都能使用所有部门，不做按身份锁部门。**

---

## 1. 一套系统 · 进门大厅

- 对外、对内都是**同一个产品入口**。  
- **进门第一眼（大厅）**：**前台接待（PMO）+ 八个部门名牌**都看得见——详见 [01-接待与分诊.md](01-接待与分诊.md)。  
  - 前台＝默认引导，**不是**唯一闸门；清楚目标或熟客可直达部门。  
- **不**做「企业版 / 代理版」两套；**不**按用户对象隐藏整个部门。  
- 总纲「客户清单只写客户能用的系统名」＝**销售/对外话术可见性**，≠ 产品里给代理师的能力对企业账号关门。

---

## 2. 用户对象（粗分，对齐老板）

| 对象 | 老板口径 | 产品上 |
|---|---|---|
| **企业客户** | 科技型中小企业；决策链上有研发负责人/CTO、老板/创始人 | 同一套系统里干活、拍板、知情 |
| **合作代理师（顾问）** | 专业交付主体；常兼签字专家 | 同一套系统里主笔专业站、签字交付 |
| **平台** | 流程/考核/运维 | 非本期「部门用户」叙事重点 |

企业客户内部谁叫发明人、谁叫 IP、谁叫老板——是**同一客户组织里的人**，不是三套产品账号体系；一期**不按这些人设部门门禁**。

研发助理＝另册增值，不进本期主用户。

---

## 3. 无部门门禁；汇报对象＝当前用户

| | 含义 |
|---|---|
| **能用** | 任一用户**可以进入任一部门** |
| **汇报** | 专家一律向**当前用户**汇报（谁在用谁就是领导） |
| **惯用** | 四方表只说明谁更常来哪一站——不是 ACL，也不改「向当前用户汇报」 |

企业可开挖掘/申请/OA；代理可开成稿——**系统不拦**。

**共享工种（例：检索专家）**：多个部门的**名册上都有这个角色**（进部门看得见）；背后同一工种，按所在部门任务逻辑干活，汇报给**当前用户**。

---

## 4. 和「看到的是否一样」

- **部门列表一样**（都能进）。  
- 默认交互仍按**最不懂 AI/专利的企业研发**设计话术；代理师用同一套，可更熟练，不另做极客壳。

---

## 5. 一单活叫什么 · 夹着什么走（现实用语）

不是「公司资产台账」，也不是「知识库」。更接近所里/公司里办一件事时的**项目案卷**。

| 产品里说 | 现实里常怎么说 | 是不是… |
|---|---|---|
| **项目 / 案件**（两名均可；对外可偏「项目」，所内可叫「案件」） | 这一单活、这个项目、这件案子 | ≠ ⑦确权后的**专利资产**；≠ 公司**知识库** |
| **案卷**（推荐代替口语「夹子」） | 卷宗、档案袋、项目文件夹 | ＝这一单的材料+记录合订；可**分类归档**，但本质是**办一件事的案卷**，不是泛知识库 |
| **交办材料 / 收件清单**（原「开工包」） | 送到某部门时：已有材料、缺什么、上家结论/问题 | 进部门时的交办附件 |
| **确认记录 / 签批痕迹**（原「汇报留痕」） | 会上点过头、签批条、确认纪要 | 领导点过头的记录，留在案卷里 |

**案卷规则（已钉）：**

1. 一单活有一份**案卷**，换部门案卷跟着走。  
2. 点过头的汇报/确认留在案卷里；换人可接着干已确认部分。  
3. **改了技术含义** → 必须再向**当时的当前用户**汇报。  

资料会分类归档进案卷；沉淀到知识库是后话，不把案卷叫成知识库。

## 6. 各部门：进入门槛 · 结束门槛（通则）

**不只申请部——八个部门各自都有「进得来 / 出得去」的门槛。**  
大厅可以点进任一部门，但**不等于**已满足该部开干或交卷条件。

| | 含义 | 例子 |
|---|---|---|
| **进入门槛** | 开干主作业前，案卷须达到本部门要求 | ⑤开写前：交底全绿+事实确认；⑥开干前：通常已有申请号/通知书 |
| **结束门槛（合格线）** | 才能开「现在做下一部门」或标本部门完成 | ④：交底全绿才交⑤；⑤：递交合格+回执才算办完 |

- 进入不过 → 补材料 / 退上部门 / 先去该去的部门，**不假装已开干**。  
- 结束不过 → **不能**合格流转到下部门（见 §7.2 工单）。  
- 具体检项由**各部门产品逻辑**自定；本条只钉「都有门槛」。

**不是统一成「进每个部门前都先查资料全不全 + 分析一遍」。**  
门槛检的是**本部门开干所必需的那几项**，因部而异：

| 类型（举例） | 进部门时主要看什么 |
|---|---|
| 上家合格交付 | 如⑤：交底全绿 + 事实确认（④工单或自带门槛检） |
| 关键件/状态到位 | 如⑥：通常要有申请号 / 通知书类材料 |
| 材料齐备 | 缺关键料才挡；不是八部同一份总清单 |
| 理解/分析 | 多属**部内接案作业**（如⑤的 A），或**大厅前台分诊**（不清楚要干嘛时）；≠ 每个部门的进入门槛本身 |

前台「上传 → 分析归档 → 材料全不全」是**分诊路径**（见 [01](01-接待与分诊.md)），熟客/直达部门仍按该部自己的进入门槛检，不强制再走一遍前台分析。

### 6.1 合格线对照（八部门 · 勿混成同一绿灯）

产品层一句话意识（细则见各部门检查表，此处不抄全文）：

| 部门 | 结束合格线（口语） | 含义 | ≠ |
|---|---|---|---|
| **① 研发立项** | **项目可引用** | 项目已建（可引用 ID/名称等）+ 方向一句话 + 状态 + 用户确认 | ≠ 论证报告已出 |
| **② 创新激发** | **路径已选题 + 收藏/跳过留痕** | 用户选题（可改推荐）后收藏进成果库，或跳过原因留痕 | ≠ 报告三图；无同级「全绿」硬闸 |
| **③ 专利挖掘** | **报告路径 ∨ 交④点包** | 讨论稿双路径：分析报告已出；和/或已确认点包可开「现在做④」 | ≠ 交底全绿；≠ ⑤过线 |
| **④ 交底** | **全绿** | 交底质检检测全绿 + 事实确认，才可「现在做⑤」 | ≠ 已可授权；≠ ⑤申请文件过线 |
| **⑤ 申请** | **过线** | 申请文件质检达递交合格（A–J 分期必跑档）+ 用户确认递交 + 回执 | ≠ ④交底全绿；≠ 已授权 |
| **⑥ 答复** | **D 过线** | 本轮答复审核（覆盖/超范围等）通过 + 用户确认递交 + 回执 | ≠ ⑤申请过线；≠ 授权结果 |
| **⑦ 维护** | **托管纪律过线** | 台账关键要素可核 + 关键期限已挂提醒；（有费用时）明白账可查、缴费经确认 | ≠ 看板已交付 |
| **⑧ 复盘** | **复盘报告本轮交付/确认** | 本轮复盘报告已交用户确认；维持/放弃已拍 **或** 显式「本轮只读不拍」留痕（未拍则不回写⑦） | ≠ 情报专报 |

**共享工种（如检索专家）：** 多部门名册可同名；**任务逻辑跟所在部门**（④薄交底向 ≠ ⑤厚申请向 ≠ ③挖点向），汇报仍给当前用户。

**多角色拍板：** 产品只认**当前用户**；组织里要「发明人确认 + 企业拍范围」→ **换人登录**即换领导，或同一人兼拍并留痕——不做按身份的部门 ACL。

**跳过①直达主链：** 允许；案卷可无正式项目容器。需要聚合键时**事后补挂/薄建项**即可，**不强迫**先过①才开④⑤（见 [02](02-研发立项.md)）。

## 7. 两种协作（部内 ≠ 部间）

### 7.1 部门内：用户 ↔ 部门负责人 ↔ 专家（全是 Agent）

产品里只有：**用户**、**部门**、**专家（均为 Agent）**。不做「平台上找真人代理人」撮合。

像所里一个组：**部门负责人**（也是专家之一）主要对用户，分配任务；活能一个专家干完就不硬拆，要专长再拆多人。前台只在大厅分诊，**不进部内派活**。

- 用户可对负责人，也可 1:1 某专家，可看产出。  
- 汇报向用户；由负责人汇总（或当事专家补充）。  

### 7.2 部门之间：工单式流转

一部门＝一业务节点。案卷跨部门用**流转工单 / 交办单**（可含批注）。

| 工单上可表达 | 含义 | 注意 |
|---|---|---|
| 现在就要做 | 接收部立刻接办 | 须满足**发出部自己的合格线**（如④→⑤须质检全绿，见交底部） |
| 以后再做 | 先挂着 | 材料不齐、用户暂不往下走等 |
| 要优化 / 退回 | 打回上部门改指定项 | — |
| 批注 | 随案卷说明 | — |

**「带病」不等于「未合格」：**  
某部合格线未过（如交底未全绿）→ **不能**开「现在做下一部门」且假装合格。  
合格线已过、但仍有非阻断说明（如用户跳过了某选做项、有已知提醒）→ 可在工单/案卷上**明示备注**后流转，不是跳过合格线。

部内达标 → 用户确认交下一部门 → 开工单 + 案卷随单。

## 8. 贯穿能力 · 与产品设计

情报官 / 查新 / 创新报告**不占**八部门编制席；用法与禁令见 [产品设计-编制总览 §4](产品设计-编制总览.md)。  
带教淡出、判断沉淀等设计钉见同文 §5；故事板见 [主链故事板](主链故事板-④⑤⑥.md)；屏上结构见 [交互大纲](交互大纲.md)。

### 8.1 老板看见什么（待办 · 薄钉）

当前用户＝领导。大厅须能看见：**待你拍的请示**、**期限催办**（主⑥⑦）、**进行中工单**——细则与部门节奏见 [交互大纲 §2.1–2.2](交互大纲.md)。  
专家自决起草默认不上老板待办；系统内提醒一期为准（⑦外发渠道缺口不超卖）。

## 9. 工程底座（产品层只钉边界）

> **会话钉（2026-10-29）：** 本产品＝**基于 DeepSeek Harness（dsh）二开的 Agent 产品**。  
> 选型细节真源：[agent-runtime-options](../../architecture/enterprise/agent-runtime-options.md) · [HARNESS](../../HARNESS.md)。产品逻辑/交互**不**重写 runtime 规格。

| 层 | 谁负责 | 产品上怎么说 |
|---|---|---|
| **① harness / runtime** | **DSH 二开**（工具环、沙箱、会话、审批协议、流式…） | **对内**叫底座；**对外 UI 禁用** Harness / Agent 编排黑话 |
| **② 领域编排** | **自有**：八部、岗表、工单、合格线、硬请示闸 | 公司 / 部门 / 专家 / 请示 |
| **③ 领域工具 + 手法** | **自有**：`各产品开发` + DomainCommand 等 | 交底/申请/OA…能力，不假装 dsh 开箱即会办专利 |

**硬结论（产品也认）：** DSH 再成熟，**不自动保证**交底全绿、申请过线、OA 策略质量；质量来自②闸门与③手法/评测。

| 产品概念 | 实现映射意识（薄） |
|---|---|
| 专家干活 / 自决推进 | harness 工具环 + 部内 Agent 会话 |
| **硬请示** | 须落到可暂停的审批/确认（对齐 dsh approval / 自有 Confirm）；**不得**只 Toast |
| 工作台主栏长文 | **产品壳**（文字知识工作台）；≠ dsh 默认 coding UI 照搬 |
| mid / workbench / agent 壳名 | 工程分包；屏上语义以 [交互大纲](交互大纲.md) 为准 |
