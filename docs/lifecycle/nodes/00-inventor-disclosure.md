## 0. 一句话讲清这个节点

**交底完成 = 把工程师脑子里的技术事实收成一份下游能用的交底包：六项技术齐套，并且权属、署名、奖酬依据、公开时点四组事实已经定死。**

要不要申请、做不做检索、立项 Go/No-Go，本节点只交出一份评分建议。决定权在立项（02）。总纲 §7 的 D1 落在立项，用这一份建议，不在交底里再判一次。节点索引把 D1/D2 放在 02。两处用同一份分数。

它不是一张表单。交底写不清，后面检索、撰写、答复、维权全部还债。交底书的上限，就是这件专利的上限。

产品化视角下，这个节点能独立成产品，因为它同时满足三条：

1. **有独立买方**：企业 IP 部门买它做内部提案管理（替代 Excel + 邮件 + 微信群）。
2. **有独立价值**：它直接决定专利质量与授权率，而质量是可以量化考核的（见 §13）。
3. **有独立边界**：它的输入是研发人员，输出是 `disclosure_pack`，不依赖检索、撰写、答复任何下游模块即可交付价值。

## 1. 节点定位与产品边界

### 1.1 在生命周期中的位置

```
研发活动 ──► 【交底】 ──交底完成──► 00b 初审 ──► 检索(01) ──► 立项(02) ──► 撰写(03) ──► …
                │                      │
                │                      └── 初审可以不进检索，把同一份建议直接交给 02
                └── disclosure_pack（IPR 批准才算完成；立案早于批准）
```

- **无 `StageId`**：它是轴外入口。交底把技术事实注入主轴，本身不是一个专利阶段。
- **产物键**：`disclosure_pack`。
- **建议路由**：`targetStage ∈ {'pre_research', 'decision'}`。立案时按这个建议建案。它不决定做不做检索，也不决定 Go。下游改阶段，不必重做交底。
- **壳与路由（原型落点）**：workbench :5174 → `/inventor`。

### 1.2 它是什么 / 不是什么

| 是 | 不是 |
|---|---|
| 技术事实的**结构化记录** | 法律文件（申请文件） |
| 撰写申请文件的**原料** | 权利要求的草稿（可以有建议，但不是正式权项） |
| 权属、署名、奖酬依据、公开时点的**定死留痕** | 奖酬发放（发放在授权公告日起 3 个月） |
| 发明人对最接近现有技术的**印象**（`prior_art_1_1`） | 检索报告（检索在 01；正式发明点在检索之后，见 00b） |
| 交给立项的**一份评分建议** | 要不要申请、Go/No-Go（决定权在 02，用这一份建议，不另打一套分） |

> 实习生最容易错的一点：把交底书写成「论文摘要」。交底书要回答的是**「别人怎么绕过你」**，不是「你的方案多先进」。

### 1.3 上下游契约

| 方向 | 对象 | 契约 |
|---|---|---|
| 上游 | 研发人员 / 创新激发活动（`InnovateCampaign` / `InventionCandidate`） | 提供技术事实、发明人及贡献、公开事实 |
| 上游 | 部门审核人 | 确认技术真实、权属初判、是否涉密、商业相关度 |
| 上游 | 法务 | 仅权属风险时会签。该会签而没有结论，IPR 不能批准 |
| 下游 | 检索调研（01） | 把 `prior_art_1_1` 当检索起点。它是印象，不是检索结论 |
| 下游 | 00b 初审 | 交底未完成不得进入。初审决定花不花钱检索，不改交底完成态 |
| 下游 | 立项决策（02） | 消费已批准的包和 §8.1 这一份建议，并在此做 D1。未批准不能 Go。02 不另打一套六维分；因检索新证据改分必须写下理由 |
| 下游 | 撰写（03） | 未批准不能撰写。交底没写的特征，撰写不能新造 |
| 横向 | 商务线（12） | 交底阶段不产生报价与发票；交底不碰 `intake_quote` |

### 1.4 独立产品的形态（如果要单独卖）

**产品名建议：交底中心 / Invention Disclosure Hub**

| 模块 | 能力 | 谁用 |
|---|---|---|
| 提报门户 | 发明人在线填单、附件、进度可见 | 研发工程师 |
| 结构化引擎 | AI 把口语化描述整理成「问题/方案/效果/特征/实施例」，并标缺口 | 发明人 + IPR |
| 齐套校验 | 6 项齐套硬闸，缺项不可提交 | IPR |
| 建议 | 六维评分 + 一条建议去向。委员会不在本节点开会 | IPR 填写；02 决议 |
| 合规留痕 | 职务发明认定、署名确认、奖酬触发、公开时点、保密审查 | 法务 / HR / 财务 |
| 交接 | 输出 `disclosure_pack`，推给检索/撰写 | 代理所 / 内部撰写 |

**不做的**：不做完整检索（那是 01）、不做权利要求撰写（那是 03）、不做官费缴纳（那是 12）。

## 2. 角色与权限矩阵

| 角色 | 代码对应 | 能做什么 | 不能做什么 |
|---|---|---|---|
| 发明人 | `inventor` persona | 填技术事实、逐人写贡献、确认 Agent 初稿、撤回本件 | 不能批准、不能立案、不能把初稿点成已批准 |
| 部门审核人 | `actingAs: 'dept'` | 确认技术真实、权属初判、涉密、商业相关度；通过则转 IP 受理；不通过则退回 | 不能立案、不能批准交底包、不能做 D1 |
| IP 受理人 | `actingAs: 'ip'`（立案） | 受理并立案、不予受理则退回、合并重复单、涉密转出时终止普通交底 | 不能代替发明人写技术事实、不能批准齐套 |
| IPR | `actingAs: 'ip'`（批准） | 核对六项与四组事实、抄录部门的商业相关度、勾一条建议、批准交底包 | 不能改发明人确认过的技术事实、不能添加发明人、不能把建议写成已 Go |
| 法务 | — | 仅在离职未满 1 年、外部合作、权属未决时会签 | 不能改技术方案、不能批准齐套 |
| 专利委员会 | `committee` persona | 本节点无动作 | 不在本节点打分或决议。D1 在 02 |
| 代理师 | `agency` | 只读协作交底状态 | 不能做部门审核 / IP 受理 / 批准 |
| 系统 Agent | `agent-disclosure` | 出结构化初稿、抽特征、把发明人印象整理进 1.1、标缺口 | 不能把印象写成检索结论；不能确认初稿；不能批准；不能空材料装完成；不能改立项报价 |

**当前实现的权限真相**（务必对实习生讲清，避免误以为是真鉴权）：

- 角色切换是**同一登录下的角色芯片**（`actingAs: 'dept' | 'ip'`），不是真实身份认证。
- 非企业工作区（代理所）整块只读，文案：「代理所工作区仅可查看协作交底状态（只读）。部门审核 / IP 受理请切换企业租户。」
- 真实产品必须换成 RBAC + 租户隔离；这条列在 §15 差距表。

## 3. 业务对象（三层，别混）

实习生最大的理解障碍是：**交底有两个状态机，长得像，含义完全不同。**

### 3.1 第一层：提报单 `InventionDisclosure`

发明人视角的「我提了一个想法」，是流程单据。

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `id` | string | 系统 | `d-<ts>` |
| `title` | string | ✅ | 发明名称 |
| `inventor` | string | ✅ | 发明人（当前是单字符串，真实产品须为数组，见 §15） |
| `dept` | string | ✅ | 部门，也是立案后的 `ownerTeam` |
| `tech` | string | — | 技术方案自由文本（当前实现只有这一个正文字段） |
| `techTheme` | string? | — | 技术主题，对齐立项 intake 的 `techTheme` |
| `patentType` | `PatentType`? | — | 默认「发明」 |
| `contact` | string? | — | 联系人，缺省「待填写」 |
| `riskDate` | string | — | **公开风险日**：已知的论文/展会/客户演示/供应商沟通日期 |
| `targetStage` | `'pre_research' \| 'decision'` | ✅ | 提交去向 |
| `status` | `DisclosureStatus` | 系统 | 见 §6 |
| `submittedAt` | string | 系统 | |
| `caseId` | string? | 系统 | 立案后回填 |
| `timeline` | `DisclosureTimelineEntry[]` | 系统 | 每次状态变化一条 |

### 3.2 第二层：交底包 `disclosure_pack`（齐套校验对象）

这是**办理交接**用的产物，不是提报单的字段。它有 6 个 REQUIRED 键（`DISCLOSURE_PACK_CHECK_ITEMS`，`packages/domain/src/handoff.ts:49`）：

| 键 | 中文标签 | 真实含义 | 合格线 |
|---|---|---|---|
| `patent_type` | 专利类型（默认发明） | 发明 / 实用新型 / 外观 | 必须显式确认，不能「默认就算过」 |
| `structure` | 结构化技术披露（问题/方案/效果） | 三段闭环 | 三段必须能对上：方案解决该问题、效果由方案产生 |
| `features` | 必要技术特征 | 独权的最小特征集 | 每条特征都「不可缺少」，删掉就不解决技术问题 |
| `embodiments` | 实施例（至少有内容） | 至少一个可复现实施例 | 有参数/材料/条件，本领域技术人员能照做 |
| `prior_art_1_1` | 现有技术 1.1 | 发明人对最接近现有技术的印象 | 至少一条，写清是什么。不是检索结果。公开号可空；写了公开号就必须带能打开的 url，编造的号作废 |
| `gaps` | 缺口清单（阻塞 / 非阻塞） | 还缺什么才能写 | 必须区分 `blocking` / `non_blocking` |

> **六项只计技术齐套。** 早期文档写过「7 项齐套」，是错的。不要把权属、署名、奖酬、公开时点塞进这六项，也不要因此改成七项。这四组是 §3.4 的批准条件：不计入 `n/6`，缺了照样不能批准。

### 3.3 第三层：案件 `PatentCase`

`advanceDisclosure(id, '已立案')` 触发 `addCase()`，映射关系：

| 案件字段 | 取值来源 |
|---|---|
| `title` | `${d.title}（研发交底）` |
| `stage` | `d.targetStage` |
| `type` | `d.patentType ?? '发明'` |
| `ownerTeam` | `d.dept` |
| `inventor` | `d.inventor` |
| `risk` | `d.riskDate ? '高' : '中'` |
| `nextDeadline` | `d.riskDate`，否则 +14 天 |
| `fulfillmentMode` | `'self_serve'`（交底阶段不派所） |
| `handoffs.disclosure_pack` | `{ status: 'drafting', note: '待结构化交底包…' }` |
| `summary` | 拼接 techTheme / tech / riskDate / contact |

**业务含义**：立案 = 从「想法」变成「有编号的在办事项」，但**此时交底包还是 `drafting`**。**立案 ≠ 交底完成。** 交底完成只看 §3.4。

### 3.4 完成契约（缺了不能批准）

批准人是 IPR。下面四组都要闭合。法条要点在 §5，这里只写字段和判据。

| 组 | 字段 | 谁填 | 不闭合就不能批准 |
|---|---|---|---|
| 权属 | `employment`：在职 / 离职未满 1 年 / 外部或兼职。`conclusion`：职务 / 非职务 / 未决 | 发明人填就业状态；部门审核人确认；未决、离职未满 1 年、外部合作必须法务会签 | 无结论，或该会签而法务未通过 |
| 署名 | `inventors[]`：姓名 + 实质贡献 | 发明人填写并确认名单 | 贡献为空，或只写「参与讨论」「提供设备」。IPR 不得添加发明人 |
| 奖酬依据 | 有规章则 `rule_version`；有约定则 `agreed_amount`；都没有则记下法定底数（发明 ≥ 4000 元，实用新型或外观 ≥ 1500 元）⚠ | IPR 登记 | 依据空缺。本节点不发放。发放时点仍是授权公告日起 3 个月 |
| 公开时点 | `disclosed`（是/否）、日期、`grace`（未公开 / 四种情形之一 / 不适用）、`foreign_plan`、`made_in_china` | 发明人填事实；IPR 核定 `grace` | 已公开但 `grace` 空着；有海外计划但未标是否在中国完成。保密审查手续在向外国申请前办完，不要求在本次批准前办完 |

法务认定「事实已清楚，但不归本单位」：权属按非职务定死，不因此终止交底。建议仍按 §8.1 勾选，交给 02。法务认定「还判断不了」：退回补充，不能批准。

人工确认与建议（同样缺了不能批准，不计入六项）：

| 项 | 谁 | 判据 |
|---|---|---|
| `ai_draft` | Agent | 只出初稿 |
| `tech_confirmed_at` | 发明人 | 确认初稿中的技术事实、特征、实施例、1.1 印象 |
| `biz_score` | 部门审核人 | 商业相关度 1–5。IPR 抄入评分卡，不得改 |
| `recommendation` | IPR | §8.1 勾唯一一条 |
| `approved_by` / `approved_at` | IPR | 六项为真、四组闭合、无 `blocking` 缺口、发明人已确认、建议已勾 |

候选发明点不另设齐套键。它就是 `features` 里的必要特征，加上 `structure` 里的效果，加上 1.1 印象。正式发明点在交底完成且检索之后确认，见 00b。

## 4. 交底书正文结构（八要素 + 1.1）

行业通行的「八要素」与申请文件说明书的六部分实质相同，只是把「发明目的/效果/实施例」从「发明内容」和「具体实施方式」里拆出来，方便发明人逐项填写。

**核心心法：交底书的每一段，都对应说明书里的一段，也对应审查员的一个问题。**

| # | 要素 | 对应说明书 | 写什么 | 合格线 | 常见错误 | 缺失后果 |
|---|---|---|---|---|---|---|
| 1 | 发明名称 | 名称 | 简明技术主题 | ≤25 字，不用商标/人名/夸张词 | 「一种革命性的…」 | 初审补正 |
| 2 | 技术领域 | 技术领域 | 「本发明涉及……技术领域」 | 不过宽（「电子技术」）不过窄（「某型号电池的某工位」） | 写成产品线名 | 分类号错误，检索不准 |
| 3 | 背景技术 | 背景技术 | 最接近的现有技术 + 其缺陷 | 缺陷必须与本发明要解决的问题**一一对应** | 贬低对手、写进自家未公开技术 | 创造性论证无靶子 |
| 4 | 发明目的 | 发明内容·要解决的技术问题 | 一句话说清要解决什么 | 可被第 6 段效果验证 | 目的写成「提高竞争力」 | 26.3 无法判断能否实现 |
| 5 | 技术方案 | 发明内容 | 完整技术方案，含全部必要特征 | **不留一手**：照做就能实现 | 只写结果不写手段（「通过 AI 优化」） | 公开不充分（26.3） |
| 6 | 有益效果 | 发明内容·有益效果 | 效果 + 支撑数据 | 有对比基线、有数据 | 「效果显著」无数据 | 创造性无支撑 |
| 7 | 实施例 | 具体实施方式 | ≥1 个可复现实施例 + 变体 | 参数、材料、条件、边界都要有 | 只写「实施例一：如图」 | 权项概括无支撑（26.4） |
| 8 | 附图 | 附图说明 | 结构图/流程图，标号一致 | 标号与文字一一对应 | 放渲染图、带尺寸标注 | 理解成本高、易出错 |
| 1.1 | 最接近现有技术 | 背景技术 | 发明人印象中的最近技术 | 写清是什么；公开号可空；有号则能打开 | 编造公开号凑条；把印象当成检索结论 | 下游从零检索，或把假号写进背景技术 |

### 4.1 「必要技术特征」怎么判定（这是最难的）

**判定法：删除测试。**

> 逐个删掉一条特征，问：方案还能不能解决第 4 段说的技术问题？
> - 不能 → 必要特征，必须进独权。
> - 还能 → 非必要，进从权或实施例。

**反例**：「一种基于深度学习的电池故障预测方法，其特征在于，使用 ResNet-50 模型。」
—— 如果换个模型也能预测，那「ResNet-50」不是必要特征，写进独权就是把保护范围白白让掉。

**正例**：「……其特征在于，以单体电压变化率与温度变化率的**比值**作为故障判据。」
—— 这个「比值」是方案的骨，删了就不成立。

### 4.2 「1.1 现有技术」为什么单独编号

1.1 是发明人印象，不是检索结果。检索报告在 01。单独编号是为了挡住两件事：把印象当成检索结论，以及编一个公开号凑齐套。

1. **印象可以没有公开号。** 写清产品、论文、展会或「不知道」即可。无号不是缺项。
2. **有公开号就必须打得开。** 打不开，该条作废，改记无号印象。禁止编造。
3. **检索从这里起步，但不把这里的文字抄成结论。** 01 另出可核验命中。
4. **防自伤。** 1.1 里若是自家尚未公开的申请，应标成内部资料，不能写成现有技术。

原型正则（`hasVerifiableResearchHitsFromSession`）只认公开号形态或 `https?://`，无号印象会被挡在齐套外。业务上无号可以通过。规则见 R00-13。

## 5. 法律底座（8 条硬规则，产品必须内置）

这一节是交底产品的**护城河**：市面上的表单工具做不到，因为它们不懂法。缺了不能批准的字段在 §3.4。本节不另立出口。

### 5.1 职务发明认定（专利法第六条 + 实施细则第十三条）

**规则**：执行本单位任务，或主要利用本单位物质技术条件完成的发明创造，为职务发明，申请专利的权利属于单位。

实施细则第十三条明确三种「执行本单位任务」：

1. 在本职工作中作出的；
2. 履行本单位交付的本职工作之外的任务作出的；
3. **退休、调离原单位后，或劳动、人事关系终止后 1 年内**作出的，与其在原单位承担的本职工作或原单位分配的任务有关的。

**产品落点**：

- 交底表单必须采集「发明人当前是否在职 / 是否离职未满 1 年 / 是否兼职或临时工作单位人员」。
- 「本单位」**包括临时工作单位**；「物质技术条件」指资金、设备、零部件、原材料、**不对外公开的技术资料**。
- 离职未满 1 年的交底，系统应自动打**权属风险旗标**，并强制法务会签。

> 这条最容易出事：员工跳槽后 11 个月提交的专利，原单位可以主张权属，哪怕新单位也参与了。

### 5.2 发明人署名（实施细则第十四条）

**规则**：发明人是指**对发明创造的实质性特点作出创造性贡献**的人。仅负责组织工作、为物质技术条件利用提供方便、或从事其他辅助工作的人，**不是**发明人。

**产品落点**：

- 交底必须逐人填写**具体贡献**，而不是只列名字。
- 贡献描述为空，或只写「参与讨论」「提供设备」：不得列入发明人。IPR 不能代为添加。
- 署名一旦随申请提交，后续更正极其困难（需办理著录项目变更并举证）。

### 5.3 奖励与报酬（专利法第十五条 + 实施细则第九十二、九十三条）

**规则**：

- **约定/规章优先**：单位可以与发明人约定，或在依法制定的规章制度中规定奖励、报酬的方式和数额（第九十二条）。国家鼓励股权、期权、分红等产权激励。
- **法定兜底**（第九十三条）：无约定也无规章时，应自**授权公告日起 3 个月内**发放奖金；一项发明专利奖金**不低于 4000 元**，实用新型或外观设计**不低于 1500 元**。若发明创造源于发明人的建议被单位采纳，应从优发给。⚠ 金额按 2023 修订文本
- **报酬**（区别于奖金）：细则不再设固定比例；2010 版曾规定的「实施后按营业利润 2% / 0.2%、许可费 10%」等比例已被删除，无约定时实务多参照《促进科技成果转化法》给予合理报酬。⚠ 需按当期文本复核

**产品落点**：

- **批准交底时**登记奖酬依据（发明人、专利类型、规章版本或约定金额、法定底数）。立案时交底尚未完成，不在立案时登记，也不要等授权才登记。
- 系统应能算「若按法定兜底，本件应发多少」，给 HR/财务一个底数。
- **奖金发放时点 = 授权公告日 + 3 个月**，这条应进 docket（当前未建，见 §15）。

### 5.4 保密与新颖性宽限（专利法第二十四条）

**规则**：申请日以前 6 个月内，下列情形**不丧失新颖性**：

1. 国家出现紧急状态或非常情况时，为公共利益目的**首次公开**的（2020 年修法新增）；
2. 在中国政府主办或承认的**国际展览会**上**首次展出**的；
3. 在**规定的学术会议或技术会议**上**首次发表**的；
4. **他人未经申请人同意而泄露**其内容的。

**程序要求**：主张宽限期须在**提出申请时于请求书中声明**，并自申请日起 **2 个月内**提交证明材料；若申请日前已知晓他人未经同意泄露，应在知晓后 2 个月内提交声明。

**产品落点**：

- `riskDate` 不是随便填的日期，它是**宽限期倒计时起点**。系统应显示：「距 6 个月宽限期届满还有 N 天」。
- 交底时必须记下：这次公开属于四种情形中的哪一种，或不适用。不适用只锁定事实。要不要还申请，写入 §8.1 建议，交给 02。
- 关键认知（讲给实习生）：**宽限期是补救，不是许可**。它不是「6 个月内申请就行」，而是「已经公开了，还能救，但要举证、要声明、而且只救这 6 个月内的公开」。

### 5.5 保密审查（专利法第十九条）

**规则**：任何单位或个人将**在中国完成的**发明或实用新型向外国申请专利的，应当**事先**报经国务院专利行政部门进行保密审查。违反规定向外国申请后再在中国申请的，**不授予专利权**——且构成无效理由。

**产品落点**：

- 交底表单必问：「是否有海外申请计划？技术是否在中国境内完成？」
- 有海外计划 → 必须标明，并标明技术是否在中国境内完成。缺标记不得批准。保密审查手续在向外国申请前完成；手续未完成的向外申请硬阻断。不要求在交底批准前办完手续。
- 这条对跨国企业/有出海业务的公司是刚需，也是「产品级 vs 表单级」的分水岭。

### 5.6 充分公开（专利法第二十六条第三款）

**规则**：说明书应当对发明作出清楚、完整的说明，以**所属技术领域的技术人员能够实现**为准。审查指南的「能够实现」= 本领域技术人员按记载内容能实现方案、解决技术问题、产生预期效果。

**产品落点**：

- 交底「技术方案」段的自动检查：是否只有功能描述（「智能识别」）而无实现手段（用什么信号、什么判据、什么阈值）。
- 「实施例」段检查：是否给出了可复现的参数/条件。
- 这两条直接决定后续会不会收到「公开不充分」的审查意见——而这是**无法通过答复挽救**的缺陷类型（不能补入新内容）。

### 5.7 非正常申请（《规范申请专利行为的规定》，2024，局令第 77 号）

**规则**（承接 2021 年《关于规范申请专利行为的办法》）：不以保护创新为目的、不以真实发明创造活动为基础，为牟取不正当利益或虚构创新业绩而提交专利申请的，属非正常申请。典型情形包括：

- 多件内容明显相同；
- 明显抄袭现有技术/现有设计；
- 不同材料、组分、配方、部件、结构或步骤的**简单替换、拼凑**；
- **编造、伪造、变造**发明创造内容、实验数据或技术效果；
- 发明创造与申请人、发明人的**实际研发能力及资源条件明显不符**。

**产品落点**：

- 这是「禁止空材料装完成」这条产品纪律的法律根据。
- 系统应记录**研发过程证据**（实验记录、样机、测试报告），并在交底与「研发能力画像」明显不匹配时提示。
- KPI 不能只考核「申请量」——那正是非正常申请的诱因。见 §13。

### 5.8 企业知识产权合规体系（GB/T 29490-2023）

**规则**：GB/T 29490-2023《企业知识产权合规管理体系要求》（2023-08-06 发布，2024-01-01 实施，替代 2013 版）对**立项、研发、采购、生产、销售、售后**各环节提出知识产权管理要求；立项环节要求对项目涉及的知识产权进行分析（检索、侵权风险）。

**产品落点**：

- 交底流程是这套体系认证的**必备证据链**之一。卖产品时可以直说：「用这个系统，认证时的研发环节记录自动生成。」
- 这也是面向国企/上市公司的销售话术支点。

## 6. 状态机（两层，必须分开读）

### 6.1 第一层：提报状态机 `DisclosureStatus`

```
草稿 ──► 已提交 ──► 部门审核 ──► IP受理 ──► 已立案
  ▲                    │            │
  └──── 退回 ◄─────────┴────────────┘
  草稿、已提交、部门审核、IP受理、退回、已立案
                └──► 已终止（撤回 / 合并 / 涉密转出）
```

**业务迁移**（谁做见下表；`已立案` 不是终态，也不是交底完成）：

| 当前 | 可迁往 | 谁 |
|---|---|---|
| `草稿` | `已提交`、`已终止` | 发明人提交；发明人可撤回 |
| `已提交` | `部门审核`、`已终止` | 系统入队；发明人可撤回 |
| `部门审核` | `IP受理`、`退回`、`已终止` | 部门审核人 |
| `IP受理` | `已立案`、`退回`、`已终止` | IP 受理人 |
| `退回` | `已提交`、`已终止` | 只允许发明人重提或撤回 |
| `已立案` | `已终止` | 发明人撤回，或 IP 受理人合并 |
| `已终止` | — | 终态 |

`退回 → 部门审核` 在业务上禁止。

**每一步的业务含义与责任角色**：

| 迁移 | 谁做 | 业务含义 | 出口条件 |
|---|---|---|---|
| 草稿 → 已提交 | 发明人 | 交给组织 | 名称、至少一名发明人、部门、公开状态已显式选择（含「未公开」） |
| 已提交 → 部门审核 | 系统 | 入队，不做判断 | 部门审核人已分配 |
| 部门审核 → IP受理 | 部门审核人 | 技术真实、权属已初判、不涉密、`biz_score` 已填 | 四项都有记录 |
| 部门审核 → 退回 | 部门审核人 | 材料不足，还要发明人改 | 结构化退回理由 |
| 部门审核 → 已终止 | 部门审核人 | 涉密，普通交底停止 | 理由 `secret_patent` |
| IP受理 → 已立案 | IP 受理人 | 建案。包仍是 `drafting` | 生成 `PatentCase`，回填 `caseId` |
| IP受理 → 退回 | IP 受理人 | 不予受理 | 结构化理由 |
| IP受理 → 已终止 | IP 受理人 | 与已有交底合并，本件关闭 | 理由 `merged`，并指向保留件 |
| 退回 → 已提交 | 发明人 | 改完重提 | 带版本。禁止不经发明人直接回到部门审核 |
| 任一非终态 → 已终止 | 发明人 | 撤回，本件不再做交底 | 理由 `withdrawn` |

原型迁移表（`AppContext.tsx:2061`）与上表不一致，只作落点记录：`草稿` 可到 `已提交`/`退回`；`已提交` 可到 `部门审核`/`退回`；`部门审核` 可到 `IP受理`/`退回`；`IP受理` 可到 `已立案`/`退回`；`已立案` 被写成终态；`退回` 可到 `已提交`/`部门审核`。原型没有 `已终止`。

**当前实现的偏差（必须在文档里点名，避免实习生照着错的理解做）**：

1. `submitDisclosure` 直接写入 `status: '部门审核'`，**跳过了 `已提交`**，但 timeline 里又补了「已提交」这一条。→ 状态机与时间线不一致。
2. `退回 → 部门审核` 允许直接跳，等于退回后可以不经发明人修改就重新进审核。
3. `草稿` 态在 UI 上不可达（一提交就是部门审核）。
4. 退回**没有理由字段**，只有 timeline 的 note 字符串。
5. 退回后重新提交**没有版本/diff**，看不出改了什么。

→ 这 5 条全部进 §15 差距表。

### 6.2 第二层：交底包状态机 `handoff`

这是通用 7 态交接机（`packages/domain/src/handoff.ts` 的 `TRANSITIONS`）：

```
drafting → submitted_to_enterprise → enterprise_review → approved → authorized_to_file → filed
                    ↕                        ↕
              changes_requested  ◄───────────┘
```

**它与提报状态机的关系**：

- 提报状态机管「这张单走到哪了」；
- 交底包状态机管「这份材料能不能交给下游用」。
- **立案时交底包仍是 `drafting`** —— 这是最容易混的一点。立案只是开了案，材料还没整理。

**下游阻断**（`guardrails.ts`）：

- `go_nogo`（立项决策）被 `disclosure_approved` 阻断：「交底包未批准：须 disclosure_pack 为已批准/授权/归档后方可 Go」。
- `draft_claims` 路径的 `approve / authorize / file / submit` 全部被 `disclosure_approved` 阻断。
- `disclosure_pack` 自身的 `approve` 被 `disclosure_pack` blockers 阻断：6 项未齐 → `交底包未齐套（n/6）· 缺项见 ConfirmBar`。

**`disclosureApproved()` 的判定口径**：`approved` / `authorized_to_file` / `filed` 三者之一。注意 **`submitted_to_enterprise` 和 `enterprise_review` 都不算批准**。业务上的批准还要满足 §3.4，不只是六项为真。

### 6.3 三个出口（互斥）

| 出口 | 落在哪 | 谁 | 何时 | 禁止混用 |
|---|---|---|---|---|
| 退回补充 | 提报 `退回`；包离开 `approved` | 部门审核人、IP 受理人，或 IPR | 材料或四组事实不够，还要发明人改 | 不是不申请 |
| 交底完成，交下游 | 包 `approved`，§3.4 闭合 | IPR | 六项为真、四组事实闭合、发明人已确认初稿、无 `blocking` 缺口、§8.1 已勾一条建议 | 不是立案。包交给下游。00b 初审决定进不进 01；02 用这份建议做 D1 |
| 终止交底 | 提报 `已终止` | 发明人，或部门审核人，或 IP 受理人 | 理由只允许 `withdrawn`（发明人撤回）、`merged`（IP 受理人合并）、`secret_patent`（部门审核人确认涉密，转出普通流程） | 不是不申请，不是技术秘密，不是防御性公开 |

同一次退回只有一个责任人：实际点退回的部门审核人、IP 受理人或 IPR。见 §6.1。

建议去向不是第四个出口。不申请、转技术秘密、防御性公开只写在 `recommendation` 里，随「交底完成」交给 02。02 可以据此 No-Go，不把提报改成 `已终止`。

下游在批准后发现写不出来：由发现方提请 IPR 撤回批准，走退回补充，交底完成取消。不另设状态。

退回满 3 次：升级到 IP 负责人督办（场景见 §12）。升级不是终止。

## 8. 评分建议（不是本节点的决定）

交底的终点是 §3.4 的交底完成。立案早于完成。要不要申请不在这里定。

本节只产出一份评分建议，随已批准的包交给 02。02 用这一份做 D1，不另打一套分。专利委员会不在本节点开会。

### 8.1 评分卡（六维，加权）

参考行业专利委员会（Patent Review Committee）通行的三维 + 法务三性，合并为六维：

| 维度 | 权重 | 打分问题 | 1 分 | 5 分 |
|---|---|---|---|---|
| 新颖性/创造性 | 25% | 与 1.1 最接近现有技术的差异是否明显 | 已被完全公开 | 明显区别且非显而易见 |
| 商业价值 | 25% | 是否落在主营产品/核心收入路径上 | 边缘试验 | 直接对应主力产品 |
| 可检测性（侵权可发现） | 20% | 竞争对手用了，能否从外部发现并取证 | 纯内部工艺，无法取证 | 体现在可拆解的产品特征上 |
| 保护广度 | 15% | 能否用较少特征覆盖较大范围 | 只能锁死一个具体实现 | 可覆盖多种实现方式 |
| 战略布局 | 10% | 是否填补布局空白 / 阻碍对手 | 与布局无关 | 关键卡位 |
| 生命周期成本 | 5% | 全球申请 + 维持 20 年的总成本是否可承受 | 成本远超价值 | 成本可忽略 |

**总分 → 建议去向**（全文只此一套。02 沿用这些阈值。本表不是 §6.3 的出口）：

| 分数 | `recommendation` | 交给 02 的建议 |
|---|---|---|
| ≥ 4.0 | `file_invention` | 建议申请发明。理由可注明「建议评估海外」。海外布局不在本节点决定 |
| 3.0–3.9 | `file_choose_type` | 建议申请。类型先用已确认的 `patent_type`（含外观）。最终类型是 02 的 D2 |
| 2.0–2.9 | `trade_secret` 或 `defensive_publication` | 必须二选一。禁止两条同时成立 |
| < 2.0 | `no_file` | 建议不申请，并写理由。提报状态仍是交底完成，不是 `已终止` |

打分责任：商业相关度一维只抄部门审核人的 `biz_score`，IPR 不得改。其余五维由 IPR 打。新颖性一维必须标 `evidence = impression`（未经检索）。检索之后若要改分，由 02 追加调整记录，不回头重开一份评分卡。

转化率只在 §13 定义一次。

### 8.2 建议必须留痕

每条建议记录：六维分、总分、`recommendation`、填写人（IPR）、日期、理由，以及被抄入的 `biz_score` 和部门审核人。02 的决议另记，不覆盖这条原文。

### 8.3 评分现状

当前 `agent-disclosure` 只做「结构化 + 齐套」，不做评分。评分建议见 R00-19，差距见 §15。

### 8.4 步骤与责任人

| 步 | 谁 | 做什么 | 完成判据 | 失败则 |
|---|---|---|---|---|
| 1 | 发明人 | 提交提报单 | R00-01、R00-46 | 停在草稿 |
| 2 | 系统 | 进入部门审核队列 | 审核人已分配 | 不分配则不得显示为已审核 |
| 3 | 部门审核人 | 确认技术真实、权属初判、涉密、`biz_score` | 通过转 IP 受理 | 材料不足 → 退回发明人。涉密 → `已终止` / `secret_patent` |
| 4 | IP 受理人 | 立案 | 生成案件，包 = `drafting` | 不予受理 → 退回发明人。重复 → `已终止` / `merged` |
| 5 | Agent | 出结构化初稿 | 有草稿，且未标已确认、未标已批准 | 空材料不得装完成 |
| 6 | 发明人 | 确认初稿中的技术事实、署名、1.1 印象 | `tech_confirmed_at` 有值 | 不确认则 IPR 不能批准 |
| 7 | 法务 | 仅权属风险时会签 | 通过，或明确「非职务」 | 判断不了 → 退回发明人。非职务 → 权属定死，仍可进入下一步 |
| 8 | IPR | 核对六项与四组事实，抄 `biz_score`，勾一条建议，批准 | §3.4 全部满足 | 缺任一项不得批准。批准即交底完成。00b 初审决定进不进检索；02 用这份建议做 D1 |

无权属风险时跳过第 7 步，不空等法务。

## 11. 期限与 SLA

### 11.1 法律期限（硬）

| 期限 | 长度 | 起算 | 后果 |
|---|---|---|---|
| 新颖性宽限期 | 6 个月 | 首次公开日 | 超期 → 公开成为现有技术，不可专利 |
| 宽限期声明与证明 | 申请时声明 + 2 个月提交证明 | 申请日 | 未声明 → 视为不主张 |
| 他人泄密的声明 | 2 个月 | 知晓或应当知晓泄露之日 | 同上 |
| 保密审查 | 事先 | 向外国申请前 | 违反 → 中国不授权 + 无效理由 |
| 奖金发放 | 3 个月 | 授权公告日 | 逾期 → 违约/违法风险 |

部门审核 5 工作日 / IP 受理 3 工作日 / 结构化 2 工作日 / 补齐 10 工作日。

### 11.3 与 docket 引擎的关系

**当前 docket 的 7 条规则（`oa1_response`、`oa_subsequent`、`application_fee`、`substantive_exam_request`、`grant_registration`、`annuity`、`pct_national_entry`）全部在立案之后**。交底阶段零期限管理。

**待补的两条**：

- `disclosure_dept_review`（部门审核 SLA）
- `disclosure_novelty_grace`（公开风险日起 6 个月宽限期倒计时）

## 13. 指标（产品化的验收尺子）

| 指标 | 定义 | 健康区间 | 说明 |
|---|---|---|---|
| 交底→申请转化率 | 申请数 / 交底完成数 | 20%–40% | 全文只此一个转化率。高于 60% 说明下游评审失效。分母是交底完成，不用提报数，也不用立案数 |
| 齐套一次通过率 | 发明人确认初稿后，IPR 第一次审核即六项为真的比例 | > 60% | 分母不是提报提交。提报提交不要求六项已齐 |
| 平均退回次数 | 每件交底被退回次数 | < 1.2 | 高 → 培训或表单有问题 |
| 部门审核时长 | 中位数工作日 | < 5 | SLA 核心 |
| 立案时长 | 提交到立案中位数 | < 10 工作日 | 端到端效率 |
| 提报完成率 | 交底完成数 / 提报数 | — | 过程量。不设区间，也不叫转化率 |
| 撰写返工率 | 撰写阶段因交底不清退回次数 | < 10% | **最能证明交底价值的指标** |
| 1.1 无编造率 | 写了公开号的条目中，url 能打开的比例 | 100% | 无号印象不进分母 |
| 首通 OA 无驳回率 | 一案授权且无实质驳回 | 越高越好 | 滞后指标，但最有说服力 |

> 卖产品时优先讲 **「撰写返工率」** 和 **「首通 OA 无驳回率」**——它们直接换算成钱（代理费 + 时间）。

## 14. 产品化切分建议

如果要把这个节点做成独立产品，建议这样切：

| 层 | 内容 | 是否可独立交付 |
|---|---|---|
| L1 表单层 | 在线交底表单 + 附件 + 进度查询 | 是（最低配，可白牌） |
| L2 结构化层 | Agent 整理问题/方案/效果/特征/实施例 + 缺口标注 | 是（差异化） |
| L3 合规层 | 职务发明、署名、奖酬、宽限期、保密审查、非正常申请 | 是（护城河，法务买单） |
| L4 建议层 | 六维评分 + 一条建议去向 + 留痕。决议在 02 | 建议可随包交付；Go/No-Go 不在此交付 |
| L5 交接层 | `disclosure_pack` 输出到检索/撰写/代理所 | 依赖下游，但可做 API |

**定价锚点**：按「立案数」计价最自然（每件 X 元），或按席位（IP 团队 + 研发提报人）。

**竞品参照系**：Anaqua / CPA Global 的交底模块偏重流程，缺中国法合规；国内表单工具缺结构化与评分。**「中国法合规 + 结构化 + 评分」三件套是空位。**

| 齐套 | 6 项 REQUIRED 全部为真 |
| 建议去向 | §8.1 的四档，全文只此一套。2.0–2.9 档在技术秘密与防御性公开中勾一个。不是本节点出口 |
| 三个出口 | 退回补充、交底完成交下游、终止交底。见 §6.3 |
| 交底完成 | §3.4：六项齐套 + 四组事实闭合 + 发明人确认初稿 + IPR 勾建议并批准 |
| 候选发明点 | `features` + 效果 + 1.1 印象。正式发明点不在本节点确认 |
