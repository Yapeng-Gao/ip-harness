## 0. 一句话讲清这个节点

**检索 = 在花钱写申请之前，先把「这件事到底新不新、别人有没有圈过地」用可核验的文献证据回答清楚，并把答案压成一份能交给决策会的结论。**

它不是「跑一遍数据库」。它是**整条专利链的证据底座**：检索结论是发明点怎么找（见 [00b](00b-invention-point-chain.md) §2.4）、权利要求怎么写、立项要不要申请、要不要改设计的证据。要不要申请在 02 定。检索做成形式主义，后面每一环都在还债。

产品化视角下，这个节点能独立成产品，因为同时满足三条：

1. **有独立买方**：企业 IP 部门买它做「申请前必过的一道证据闸」；代理所买它做出报告的流水线。FTO / 尽调侵权风险见独立节点 [01b](01b-fto.md)（**P02b**），不在本节点主售。
2. **有独立价值**：一次正式检索的市价约 ¥3,000–15,000 ⚠（按范围），而一次误判导致的无效撰写 + 重复申请，成本是它的数倍。
3. **有独立边界**：输入是技术方案 + 交底里的 1.1，输出是 `research_report` 与可核验命中集，不依赖撰写、答复、维持任何下游模块即可交付。

## 1. 节点定位与产品边界

### 1.1 在生命周期中的位置

```
交底(00) ──► 【调研/检索 01】 ──► 立项决策(02) ──► 撰写(03) ──► 审查(04) ──► …
   │                │                    │
   │                └─ research_report   └─ 消费：可专利性结论（FTO 风险档可空）
   └─ prior_art_1_1（检索起点，非检索结果）

         （按需，不堵申请）──► 【01b FTO】──► 上市/定型决策
```

代码里的阶段定义（`packages/domain/src/stages.ts:10`）把本节点拆成三个概念 runner：

| runner | 名称 | 步骤 |
|---|---|---|
| `prior_art` | 现有技术检索 | 定关键词分类号 → 多库并行检索 → 筛选标注 → 生成报告 |
| `fto` | 初步 FTO（**可选附件**） | 申请主链**不强制**。若触发上市/定型等条件，走完整规格 [01b-fto.md](01b-fto.md)；本 runner 仅历史概念目录，不得把申请齐套绑死在 FTO 上 |
| `patentability` | 可专利性初评 | 梳理要点 → 对比最接近现有技术 → 给结论 |

> **注意**：`runners` 是静态概念目录，不是案级进度（`packages/domain/src/types/index.ts:123` 已标 `@deprecated`）。案级进度只认 `flowProgressByCase[caseId].research`。

### 1.3 它是什么 / 不是什么

| 是 | 不是 |
|---|---|
| 一份**有证据链**的现有技术盘点 | 一份「查了一下，没查到」的说明 |
| 可专利性初判的**输入** | 授权前景的**承诺**（审查员不受检索报告约束） |
| （可选）FTO 初评风险档草稿；**正式 FTO 在 01b** | 法律意见书；亦不得代替可专利性结论 |
| 撰写阶段选择最接近现有技术的**依据** | 权利要求草稿（那是 03） |
| 一次可复盘的**检索式 + 命中 + 结论**三元组 | 一次性的聊天式问答 |

> 实习生最容易错的一点：把 `prior_art_1_1` 当成「已经检索过了」。1.1 是**发明人凭印象写的最接近条目**，是检索的**起点**（[00b](00b-invention-point-chain.md) §4.2），不是检索结果。检索必须自己重建检索式，不能顺着 1.1 抄一遍。

### 1.5 独立产品的形态

**产品名建议：检索与可专利性评估台 / Prior Art & Patentability Desk**（**不再**称 “& FTO Desk”；正式 FTO 产品见 01b / P02b）

| 模块 | 能力 | 谁用 |
|---|---|---|
| 检索式工作台 | 关键词 × 分类号 × 申请人 × 时间窗的布尔式、同族折叠、跨库同义扩展 | 检索员 / IPR |
| 命中台账 | pubNo 可核验、原文链接、相关度、X/Y/A/E/P 分类、同族归并 | 检索员 / 代理师 |
| 报告分流 | 科技查新 / 可专利性检索（两种主模板）；FTO 模板归属 **01b** | 企业 IP / 代理所 |
| 结论绑定 | 每条结论必须挂到具体命中（`binding`） | 企业 IP（评审用） |
| FTO 初评（可选附件） | 仅当业务触发时附风险档草稿；**不进申请主链必齐套**；深评进 01b | 企业 IP / 法务 |
| 交付与交接 | `research_report` **6 项必齐** → 7 态交接 → 立项会 | 代理所 / 企业 |

**不做的**：不写权利要求（03）、不替代 CNIPA 的专利权评价报告、不出具法律意见、不做实时侵权监测（07）、**不把正式 FTO 绑进申请交付**（01b）。

## 2. 角色与权限矩阵

| 角色 | 代码对应 | 能做什么 | 不能做什么 |
|---|---|---|---|
| 企业 IP / IPR | `persona = 'enterprise_ip'`（`persona.ts:22`） | 配置检索范围、审阅命中、确认结论、批准/授权/归档 `research_report`、Go 前把关 | 不能代替代理所做正式检索的署名 |
| 代理所检索员 / 代理师 | `persona = 'agency'` | 起草报告、提交企业、归档；可走 `approve_strategy` HITL 链 | 不能确认企业结论（`approve` 属 enterprise） |
| 评审委员 | `persona = 'committee'` | 只读 `research_report` 供立项投票 | 不可提交 / 批准 / 授权 / 归档（`persona.ts:97-112`） |
| 发明人 | `persona = 'inventor'` | 只读自己的案件、在门户提供技术线索 | 工作台交接动作全禁（`persona.ts:89-95`） |
| 系统 Agent | `agent-research`（core 档） | 关键词扩展、商业库检索、命中聚类、可专利性草稿；（可选）FTO 初评要点草稿 | 不能空命中过闸；不能改立项报价；**不能**用 FTO 草稿代替 01b |

**当前实现的权限真相**（务必对交付方讲清）：

- 角色切换是**同一登录下的 Persona 芯片**，不是 SSO/RBAC（`persona.ts:1-4` 注释「演示可执法，非真 SSO/IAM」）。
- Agent 侧与工作台侧各有一套闸，但共用同一份 domain 函数（`guardrails.ts:190` 的 `hasVerifiableResearchHitsFromSession` 被 `AgentContext.tsx:161` 复用），这是有意的「唯一入口」，不是重复。
- **代理所工作区可写，不是因为权限细，而是因为 `FulfillmentMode = delegated` 时为 agency 放行 `save_draft / submit / file`**（`handoff.ts:188`、`handoff.ts:222-237`）。

### 2.1 决策权

角色矩阵回答「谁能做什么」，不回答「谁说了算」。本节点有一处结构性错位必须点破：**最懂检索方法的人，恰恰最不该下可专利性结论**。划分依据 [decision-rights.md](../decision-rights.md) §1、§3.1。

**四种权能在本节点的落点**

| 权能 | 典型场景 | 持有者 |
|---|---|---|
| 建议权 | 检索式怎么搭、选哪些库、结论倾向、要不要补检索 | 检索员 / 代理师 / 系统 Agent |
| 决定权 | 采纳哪份结论、要不要继续花钱、是否送进 02 | 企业 IP 负责人 |
| 否决权 | 预算超限、涉密项目、保密审查未判 | 财务 / 法务 |
| 知情权 | X 类命中、负向结论、结论有效期 | 发明人 / 业务部门 / 评审委员 |

**决策归属**

| 决策 | 建议者 | 决定者 | 否决者 | 级别 | 依据 / 条件 |
|---|---|---|---|---|---|
| 检索范围：数据库组合 | 检索员（按技术领域出方案） | 企业 IPR | 法务（涉密项目） | L1 | 至少覆盖专利库 + NPL 层；涉外须加英文库 |
| 检索范围：时间窗 | 检索员 | 企业 IPR | — | L1 | `dateWindow.to` ≥ 优先权日（R01-06） |
| 检索范围：语言 | 检索员（提示漏检） | 企业 IPR | — | L1 | 中/英至少两语种；未覆盖须声明 |
| 是否委托外部检索 | IPR、代理师 | 企业 IP 负责人 | 财务 | L2 | 见 §8.1；高价值、涉外、多语种必须外委 |
| 检索方法与检索式 | 检索员 | 检索员（专业判断） | — | L1 | 企业不指定布尔式，只定范围与目的 |
| 命中可核验性判定 | 系统校验 + 检索员自查 | 提交方（检索员 / 代理师） | IPR（复核可退回） | L1 | pubNo + url 双校验；不得由批准人代判 |
| 检索报告签署 | 检索员起草 | IPR（企业侧）/ 代理师（外部报告） | — | L2 | 签署人对方法可复现与命中可核验负责 |
| 可专利性结论 | 检索员 / 代理师起草 | 具备资格的 IPR 或代理师签署 | — | L2 | 未签署的结论不得进入 02 |
| 是否采纳结论 | IPR | 企业 IP 负责人 | 法务（权属 / 合规） | L2 | 「采纳」不等于「申请」，后者在 02 |
| 是否因结论不利放弃申请 | IPR、代理师 | IP 总监（D1，02 的 Go/No-Go） | 法务、财务 | **L4** | 不可逆；01 只出结论，不结案 |
| 报告对外提供（投资方 / 客户） | 业务、IPR | 企业 IP 负责人 + 法务会签 | 法务 | L3 | 须脱敏；不提供原始工作底稿 |

**三层责任，不得合并**

| 层 | 谁 | 对什么负责 | 明令不得做 |
|---|---|---|---|
| 执行层 | 检索员 / 代理师 | 检索式可复现、命中可核验（pubNo + url）、分类与理由 | **不下可专利性结论**，不判断是否申请 |
| 判断层 | 具备资格的 IPR 或代理师（签署） | 新颖性 / 创造性判断有命中支撑（`binding`） | 不代替企业决定是否采纳 |
| 决策层 | 企业 IP 负责人 | 采纳与否、是否进 02、预算 | 不直接改命中，不替签署人改结论文字 |

> 一句话：检索人对「查得对不对」负责，签署人对「判断成不成立」负责，IP 负责人对「用不用、花不花这笔钱」负责。三件事在系统里必须是三个签字栏，不能是一个「审批通过」按钮。

**「暂不建议申请」不是终局结论**

| # | 要求 |
|---|---|
| 1 | 须写明书面理由：哪几篇构成 X 类、逐特征比对结论、为何无法通过限缩或补充数据规避 |
| 2 | 由签署人（IPR / 代理师）签署，企业 IP 负责人确认已知悉 |
| 3 | 结论作为 02 的 No-Go 输入；**01 无权结案、无权改提报状态** |
| 4 | 02 阶段仍可提出限缩方案或补充实验数据，报告须能开新版本重评 |
| 5 | 发明人有知情权，异议书面记录并随案流转，不得删除 |

**预算分级**（金额为示意 ⚠，按企业授权制度配置，不得硬编码）

| 级别 | 单次检索预算 | 批准人 | 典型情形 |
|---|---|---|---|
| L1 | ≤ 1 万元 ⚠ | IPR | 单库、内部执行、初步检索 |
| L2 | 1–5 万元 ⚠ | 企业 IP 负责人 | 单国正式检索 + 逐篇比对 |
| L3 | 5–20 万元 ⚠ | IP 总监 + 财务 BP | 多国 / 多语种、NPL 深检、含 claim chart |
| L4 | > 20 万元 ⚠ | 总经理 / 授权代表 | 涉外多国、尽调级检索、与无效程序联动 |

**决策权规则**

| ID | 规则 | 现状 |
|---|---|---|
| R01-50 | 检索范围三要素（数据库、时间窗、语言）须由企业 IPR 确认并留痕；检索人不得单方缩窄 | ❌ |
| R01-51 | 是否委托外部检索由企业 IP 负责人按预算分级决定；代理所不得自行加做后要求付费 | ❌ |
| R01-52 | 检索人对方法与可核验性负责，不得出具可专利性结论；结论须由具备资格的 IPR 或代理师签署 | ❌ |

| R01-59 | 报告对外提供（投资方、客户、尽调）须企业 IP 负责人 + 法务会签，且只提供签署版：脱敏后的结论与命中清单，不提供工作底稿 | ❌ |

### 3.5 三张纸，别混（本节点最容易出事故的认知）

中文语境把「查新」当动词用，实际是三份目的不同的报告。详见 [00b](00b-invention-point-chain.md) §1，此处落到**产品产物对象**上：

| 名称 | 出具方 | 回答的问题 | 结论口径 | 产品落点 | 专利法效力 |
|---|---|---|---|---|---|
| 科技查新报告 | 科技部/教育部认定的查新机构 | 国内外是否已有相同或类似**研究报道** | 「未见相同报道」——比新颖性**宽** | `kind: 'novelty_check'`，独立模板、独立交付 | **无**，审查员不采信 |
| 专利检索报告（可专利性） | 代理所 / 企业 IPR / 商业数据库 | 是否具备新颖性、创造性，能否授权 | 单篇对新颖性、组合对创造性 | `kind: 'patentability'`，挂 `research_report` | 有参考价值，非法定文件 |
| FTO 检索报告 | 代理所 / 律所 | 实施该技术是否**侵犯他人专利权** | 权利要求逐项比对 + 风险分级 | `kind: 'fto'`，挂 `fto` 子对象 | 无，但是侵权预警的唯一依据 |

**三者不可互换的三条硬理由**：

1. **结论口径不同**：查新「未见相同报道」不要求单篇公开全部特征；专利新颖性要求**单篇公开权利要求的全部技术特征**（《专利审查指南》第二部分第三章）。用查新撑「可以申请」在逻辑上不成立。
2. **检索对象不同**：可专利性检索找**任何已公开的技术**（含论文、展会、销售）；FTO 只找**目标市场内、仍然有效**的**权利要求**（`status = 有效`、未过期、未无效）。FTO 检索到的 expired 专利不构成障碍，但对可专利性检索仍是现有技术。
3. **时间基准不同**：可专利性以**申请日/优先权日**为界；FTO 以**实施日**为界，且结论有保鲜期（新专利持续公布，结论会过期）。

| 误用 | 直接后果 | 次生后果 |
|---|---|---|
| 用查新报告代替可专利性检索 | 结论偏乐观，误判可申请 | 撰写时找不到真正的 X 类文献，独权写宽 → 一通即缩权 |
| 用可专利性检索代替 FTO | 忽略他人有效权利要求 | 产品上市后被诉，赔偿或被迫改设计 |
| 用 FTO 结论说「可以申请」 | 混淆「不侵权」与「可授权」 | 两者互相独立：可能不侵权但不可专利，也可能可专利但侵权 |
| 只做一次检索覆盖两个目的 | 检索式、时间窗、法律状态过滤全错 | 报告无法用于任一目的 |

### 3.6 对比文件分类 X / Y / A / E / P

国际通行标注法（WIPO ST.14 的 relevance 类别，PCT/EPO 检索报告均用）。检索环节的标注直接决定后续结论与撰写：

| 标记 | 含义 | 对结论的影响 | 对撰写的影响 |
|---|---|---|---|
| **X** | 单独一篇即破坏新颖性或创造性 | 新颖性 `无` 或创造性 `低` | 必须避开；发明点要重新找（00b §2.4） |
| **Y** | 与另一篇结合破坏创造性 | 创造性 `低`，新颖性可能仍在 | 权项需加入「组合非显而易见」的特征 |
| **A** | 一般背景技术，不影响三性 | 无 | 写进背景技术段落 |
| **E** | **抵触申请**：申请日在前、公开日在后 | 只破坏**新颖性** | 不能论创造性；若为自家在先申请，需评估重复授权（法 9） |
| **P** | 优先权日与申请日之间的文献 | 需核实是否构成抵触申请 | 决定优先权主张是否有效 |

**三条法条口径必须分清**（《专利法》第二十二条 ⚠）：

- **新颖性（22.2）= 单独对比**。一项权利要求作为一个整体，与**一项**现有技术中的**一个**技术方案比较；「单独」指一个技术方案，不是一篇文献（一篇文献可含多个方案）。
- **创造性（22.3）= 组合对比**。多篇结合 + 技术启示判断（三步法）。
- **抵触申请**：任何单位或个人（含申请人自己）就同样的发明在申请日以前向国务院专利行政部门提出过申请、并记载在申请日以后公布的专利申请文件中。**破坏新颖性，不属于现有技术，不能用于论创造性** ⚠。

> 常见错误：拿两篇文献拼起来否定新颖性。那是创造性论证，不是新颖性论证。若产品把这条写错，出具的报告在无效程序里会被直接打掉。

代码现状：`relevance` 只有「高/中/低相关」三档（`types/index.ts:488`），**没有 X/Y/A/E/P 字段**，也没有 `E` 类所需的「申请日 / 公开日」双日期。这是本节点最该补的 schema 缺口。

### 4.2 两条已实现规则为什么重要（产品护城河）

`hits_verifiable` 与 `binding` 是仓库里少见的两条「比多数商用产品更细」的设计（[00b](00b-invention-point-chain.md) §4.1 已点名）。它们的价值不在校验本身，在**改变了交付物的性质**：

- **`hits_verifiable` 防编造**。行业里大量「检索报告」的对比文件是凭印象写的，甚至编公开号。代码在两条路径上做了同一件事：
  - Agent 侧：`hasVerifiableResearchHitsFromSession`（`guardrails.ts:190-219`），用正则 `/(?:CN|US|EP|WO|JP)[A-Z0-9]{5,}/i` + `https?:\/\/`，扫会话步骤与产物正文；
  - 工作台侧：逐条命中检查 `pubNo?.trim()` 与 `url?.trim()`（`ResearchFlow.tsx:101-112`）。
  - **两条路径的正则口径不一致**：Agent 侧校验公开号前缀与长度，工作台侧只校验非空。结果是同一份数据可能过一边、不过另一边。
- **`binding` 防「有文献无结论」**。命中和结论是两个独立字段，产品强制二者相连，等于把「结论从哪来」变成可审计的事实。这是后续答复 OA、无效程序里唯一能自证检索尽责的材料。

**E1「快速检索」的边界（最常被滥用的一条）**

| 判断项 | 问什么 | 不满足则 |
|---|---|---|
| 是否已声明 | 报告首屏写明「快速检索，未穷尽」 | 不得提交 |
| 是否覆盖分类号 | 至少 1 个主 IPC/CPC 分类号 + 2 组关键词 | 视为未检索 |
| 结论口径是否收窄 | 只能出「可申请 / 有条件可申请 / 待定」，不得出终局负向结论 | 结论项置灰 |
| 是否有补检计划 | 写明补检时点与责任人 | 不得批准 |
| 是否进入立项 | 快速检索结论只能支撑「是否花钱做正式检索」，不能单独支撑 Go | 02 的 Go 闸须拦截 |

> **例外不是豁免**：每条例外须记录批准人、批准时间、理由、有效期，只对本案生效；并在 §12 按季度统计例外率。**E1 与 E5 合计占比超过三成，说明流程或资源本身有问题，不是执行问题。**

### 4.8 规则冲突与裁决

规则之间会打架。不预先给裁决顺序，实际执行就由「谁催得急」决定。

**四类真实冲突**

| # | 冲突 | 典型表现 | 裁决 | 裁决人 |
|---|---|---|---|---|
| C1 | 检索要全 vs 时间要快 | 立项会明早开，检索只跑了一半库 | **先交已完成的检索 + 明确标注未覆盖范围**，不假装完整；未覆盖范围写入报告，02 在知情下决策 | 企业 IP 负责人；检索人不为压缩范围背书 |
| C2 | 结论保守 vs 业务要上 | 检索人判「暂不建议申请」，业务说这个产品必须报专利 | **结论不得改，路径可以改**：02 可选择限缩方案、补充数据、转技术秘密或防御性公开。**报告不得因业务压力被改写** | 结论归签署人；是否申请归 IP 总监（D1，L4） |
| C3 | 外部检索贵 vs 内部能力不足 | 预算 ¥3k–15k ⚠ 一次，IPR 认为自己做也行 | 按**案件价值 / 涉外与否 / 语种数**三项定档：涉外、多语种、拟主张优先权 → 必须外委；纯国内低价值 → 内部初步检索 + 抽检 | 企业 IP 负责人批预算；财务可否决超限 |
| C4 | 命中高相关 vs 但已失效 | 一篇 X 类文献法律状态为失效 / 未进入中国 | **分目的处理**：可专利性检索中失效文献**仍是现有技术**，照常引用；FTO 中同一篇**不构成障碍**。同一命中在两个目的下结论相反是正常，不是矛盾 | 签署人按 `kind` 分别判定，不得合并出一份「综合结论」 |

## 5. 法律底座 / 行业规则

### 5.1 新颖性：单篇对比（《专利法》第二十二条第二款 ⚠）

**规则**：新颖性要求不属于现有技术，且无抵触申请。判断时把一项权利要求作为一个整体，与一项现有技术中的一个技术方案比对，**全部技术特征**被公开才丧失新颖性。

**产品落点**：X 类标注 `citationCategory = 'X'` 后，系统必须要求「逐特征比对表」至少有一行，否则不允许把结论置为「暂不建议申请」。比对表就是 claim chart 的雏形。

**失效后果**：若把两篇文献拼起来判「无新颖性」，结论在无效/复审阶段站不住；更糟的是反向错误——把实际已被单篇公开的方案判为「有新颖性」，导致写了一篇注定被驳的申请，白花代理费与 2–4 年时间。

### 5.2 创造性：组合对比与三步法（第二十二条第三款 ⚠）

**规则**：与现有技术相比，突出的实质性特点 + 显著的进步。审查指南三步法：确定最接近的现有技术 → 确定区别特征与发明实际解决的技术问题 → 判断对本领域技术人员是否显而易见。

**产品落点**：Y 类必须**成组**出现（至少 2 篇，且系统记录「为什么结合」）。单篇 Y 是无效标注，应在保存时拦截。

**失效后果**：Y 类标注不成组 → 撰写时拿不到「组合非显而易见」的论证素材 → 独权没有梯度，第一次 OA 就被迫大幅缩权。

### 5.3 抵触申请（第二十二条第二款后半 ⚠）

**规则**：他人在申请日以前提出、在申请日以后公布的中国申请，构成抵触申请；**只破坏新颖性，不属于现有技术，不能用于论创造性**。申请人自己的在先申请同样可能构成抵触申请（实务中通常先触发重复授权问题，法 9）。

**产品落点**：E 类命中必须绑定**双日期**（申请日、公开日）与申请人字段；系统检测到 `assignee === 本方` 时打「自家在先申请」旗标。

**失效后果**：系列案（同一申请人的关联申请）最高发。漏检或误判会直接导致后一案被驳，且补救手段极其有限。

### 5.4 现有技术的时间基准（第二十二条第五款 ⚠）

**规则**：现有技术是**申请日以前**在国内外为公众所知的技术；主张优先权的，以优先权日为准。

**产品落点**：检索的 `dateWindow.to` 必须 ≥ 优先权日；报告必须显示「检索截止日」与「优先权日」两个日期，并计算二者的差值（差值 > 0 表示存在漏检风险）。

**失效后果**：检索截止日早于优先权日 = 主动放弃最后一段时间的文献，是最常见的「报告看起来很专业但漏了关键一篇」的原因。

### 5.5 抵触与宽限期（第二十四条 ⚠）

**规则**：申请日前 6 个月内，四类情形（国家紧急状态首次公开、中国政府主办/承认的国际展览会首次展出、规定学术/技术会议首次发表、他人未经同意泄露）不丧失新颖性；须在申请时声明并在 2 个月内提交证明。

**产品落点**：检索必须能识别「自家已公开」的文献——若命中里出现本方在 `riskDate` 之后公开的论文/展会资料，系统应提示「此文献可能落在宽限期内，需声明举证」；否则会被误判为破坏新颖性的 X 类。

**失效后果**：把自家 6 个月内的公开当成 X 类，导致放弃申请；或反之，把 6 个月外的公开当成「还能救」，实际已毁新。

### 5.6 保密审查（第十九条 ⚠）

**规则**：在中国完成的发明或实用新型向外国申请专利前，须事先报经国务院专利行政部门进行保密审查；违反的，在中国不授予专利权，且构成无效理由。

**产品落点**：检索阶段就要采集「目标市场 / 是否海外布局」。若答案为「有海外」，则检索报告须附「保密审查已判断」标记，未标记的不得进入 02 的 Go。

**失效后果**：跨境企业最容易踩。检索报告是这条合规链上第一个能拦住它的节点，因为它是唯一在申请前就讨论「目标市场」的环节。

### 5.7 诚实信用与非正常申请（《专利法》第二十条；《规范申请专利行为的规定》2024，局令第 77 号 ⚠）

**规则**：申请专利应当遵循诚实信用原则；不以保护创新为目的、无真实研发基础、编造伪造变造发明创造内容/实验数据/技术效果的，属非正常申请。

**产品落点**：检索报告里的对比文件同理——编造公开号、伪造命中，是「编造材料」的一种。`hits_verifiable` 的产品价值就是让这条法律要求变成**机器可判**。

**失效后果**：非正常申请被认定后，不予减缴、通报、影响企业信用与后续申请；对代理所是执业风险。

### 5.8 专利权评价报告（实用新型 / 外观）⚠

**规则**：专利侵权纠纷涉及实用新型或外观设计的，法院或管理专利工作的部门可以要求权利人出具由国务院专利行政部门作出的专利权评价报告（《专利法》相关条款 ⚠ 条号按当期文本复核；《专利法实施细则》（2023 修订）规定 CNIPA 自收到请求书后一定期限内作出，⚠ 期限与条号需复核）。

**产品落点**：本节点对实用新型/外观只能出「检索意见」，不能出「可专利性结论」。产品上必须按 `PatentCase.type` 分流模板，并在报告页写明「正式评价以 CNIPA 评价报告为准」。

**失效后果**：拿代理所的检索报告去应诉，法院不认；企业以为已有「官方背书」，错过请求评价报告的时点。

### 5.9 立项环节的知识产权分析（GB/T 29490-2023）

**规则**：企业知识产权合规管理体系要求在产品立项/研发环节对涉及的知识产权进行分析（检索与侵权风险）。

**产品落点**：本节点的 `research_report` 就是这条要求的证据。销售话术：认证审核时，检索记录、检索式、结论绑定可一键导出。

## 6. 状态机

### 6.1 外部状态：`research_report` 走通用 7 态交接机

```
drafting ──submit──► submitted_to_enterprise ──start_review──► enterprise_review
   ▲                        │                                        │
   │                        │◄──────── request_changes ──────────────┤
   └──── changes_requested ◄┘                                        │
                                                                     ▼
        filed ◄──file── authorized_to_file ◄──authorize── approved ◄┘
```

合法迁移见 `packages/domain/src/handoff.ts:147-186`。本节点的语义映射：

| 动作 | 角色 | 本节点业务含义 | 出口条件 |
|---|---|---|---|
| `save_draft` | agency | 存草稿，检索未完成 | — |
| `submit` | agency | 检索报告交企业评审 | 7 项齐套 |
| `start_review` | enterprise | 企业开始核对 | — |
| `request_changes` | enterprise | 退回补检索 | 填 annotation |
| `approve` | enterprise | 结论被采纳 | 7 项齐套 + `hits_verifiable` |
| `authorize` | enterprise | 标签是「确认可立项」 | 仅企业 |
| `file` | agency | 报告归档 | — |

> **口径警告**：`authorize` 的中文标签是「确认可立项」（`handoff.ts:340`），但**真正的立项闸是 02 的 Go**。两个「可立项」并存会让用户以为 research 的 approve 就等于立项通过。产品文案应改为「确认检索结论可用于立项」，把决定权留在 02。

### 6.2 内部进度：5 步（代码只有 4 段 stepper）

`src/data/flowSteps.ts:19-26` 定义 5 步：检索配置 → 结果研判 → 可专利性 → FTO 初评 → 结论提交。**业务口径**：第 4 步为条件触发/可跳过；正式 FTO 不在本 Flow 闭环。

`ResearchFlow.tsx:284-293` 的 `progressStep` 只推 0–4，其中 4 表示「已交接」而非「结论提交」：

| step | 触发条件 | 语义 |
|---|---|---|
| 0 | `keywords` 非空或 `databases.length > 0` | 检索配置 |
| 1 | 勾选 ≥1 命中 | 结果研判 |
| 2 | 有结论或有研判笔记 | 可专利性 |
| 3 | `ftoReady` 或（风险档 + 结论） | FTO 初评 |
| 4 | handoff ∈ submitted/enterprise_review/approved/authorized/filed | 已交接 |

### 6.3 当前实现的偏差（逐条点名）

1. **stepper 与目录不同步**：目录 5 步，stepper 4 段 + 完成态，「结论提交」不占格（`flowSteps.ts:24` vs `ResearchFlow.tsx:284-293`）。
2. **`conclusion` 恒非空**：初值来自 seed（`ResearchFlow.tsx:76`），下拉四选项都非空，因此 R01 的 `conclusion` 项**永远为真**，必填校验是死代码。
3. **`kw` / `db` 亦来自 seed**：新建案件若不带 seed，`loadSeed` 回落到 `researchSeed.c2`（`ResearchFlow.tsx:40-42`），把固态电池的关键词灌给任意案件。这是最严重的「串案」风险。
4. **滑杆被自动覆盖**：勾选变化时以 seed 为基线重算 `novelty/inventiveness`（`ResearchFlow.tsx:161-167`），用户手工拖的值会被丢弃。
5. **自动结论只能往乐观方向走**：`ResearchFlow.tsx:183-187` 只会写「有条件可申请」或「可申请」，**永远不会**写「暂不建议申请」；即使拖到 5 分也一样。负向结论只能人工选。
6. **命中相关度只有三档**，无法表达 X/Y/A/E/P（`types/index.ts:487`）。
7. **`hits_verifiable` 两套口径**：工作台只看非空，Agent 看正则（`guardrails.ts:200`），同一份数据两边结论可能不同。
8. **c3「完成竞品专利分析」在提交时被一并勾选**（`ResearchFlow.tsx:675`），但流程里没有任何竞品分析步骤或字段。
9. **`toIntake` 走 `advanceStage` 命令**（`ResearchFlow.tsx:265-272`），而 `advanceStage` 分支调用 `advanceFromWorkbench` 时**不传 `resolveDoneIds`**（`AppContext.tsx:2669-2676`），因此完全依赖此前 `approve` 时已勾 c5。

## 8. 步骤序列 / 工作流

### 8.1 两种检索，两个价签

| | 初步检索（IPR） | 正式检索（代理所 / 检索机构） |
|---|---|---|
| 执行方 | 企业 IPR | 代理师 / 检索员 |
| 耗时 | 0–2 个工作日 | 3–10 个工作日 ⚠ |
| 成本 | 内部人力，0 元增量 | ¥3,000–15,000 ⚠（按范围、国别、语言、是否含 claim chart） |
| 数据库 | 免费库：CNIPA 检索系统、Espacenet、Google Patents、PATENTSCOPE | 商业库：IncoPat / 智慧芽 / Derwent / Orbit 等 |
| 目的 | 快速判断「还有没有戏」，值不值得花钱 | 出正式报告，支撑撰写与决策 |
| 产出 | 粗筛命中 + 口头结论 | `SearchReport` + 逐篇比对 + 结论 |
| 失败回退 | 结论写明「暂不建议申请」或建议转技术秘密，交给 02。不结案，不改提报状态 | 退回补检索（`request_changes`） |

> 产品必须把这两次检索做成**两个独立记录**（`SearchStrategy` 数组），否则「正式检索花了一家所的钱，结论却和 IPR 的粗筛一样」这类争议无法复盘。

### 8.2 完整步骤

| # | 步骤 | 谁做 | 耗时 | 产出 | 完成条件 | 失败回退 |
|---|---|---|---|---|---|---|
| 1 | 接案与范围确认 | IPR + 发明人 | 0.5 天 | 目标国别、技术主题、关键实施方式 | 范围共识 | 退回交底补技术细节 |
| 2 | 检索式构造 | IPR / 代理师 | 0.5–1 天 | `SearchStrategy`（A/B/C 三块 + 布尔式） | 三个块都有词/号 | 词太宽 → 加分类号；太窄 → 拆块 |
| 3 | 多库执行 | IPR / 代理师 | 0.5–2 天 | 原始命中集（未筛选） | ≥1 库有结果 | 换同义词 / 换库 / 降级到语义检索 |
| 4 | 筛选与分类 | 代理师 | 1–3 天 | 命中台账 + X/Y/A/E/P | 每篇有分类与一句话理由 | 分类存疑 → 加 A 类保守处理 |
| 5 | 结论与绑定 | 代理师起草 / IPR 确认 | 0.5–1 天 | 新颖性/创造性/结论 + `binding` | 结论均挂命中 | 结论无支撑 → 回 4 |
| 6 | FTO 初评（**可选**） | 代理师 / 法务 | 0.5–2 天 | 仅触发时：草稿或升 01b | 业务上可跳过；代码仍看 `ftoReady`（债） | 高危 → **必须**升 01b 深评，不得用初评定上市 |
| 7 | 交接与归档 | agency → enterprise | 0.5 天 | `research_report` 7 态 | **6 项必齐** + 批准（业务口径） | 退回补检索 |

### 8.3 每步的「完成条件」必须是可判定的

反例：「检索充分」。正例：「`SearchStrategy.databases.length ≥ 2` 且其中至少一个为非中文库（涉及涉外时）」。

## 10. 期限与 SLA

### 10.1 本节点没有官方法定期限

检索本身不产生任何 CNIPA 期限。这是它和 04/05 的根本区别——**它的紧迫性全部来自上下游**：

| 约束 | 长度 | 起算 | 失效后果 |
|---|---|---|---|
| 优先权窗口 | 12 个月（发明/实用新型）⚠ | 首次申请日 | 超期不能主张优先权，后一申请以实际申请日为基准 |
| 新颖性宽限期 | 6 个月 | 首次公开日 | 超期 → 公开成为现有技术 |
| 保密审查 | 事先 | 向外国申请前 | 违反 → 中国不授权 |
| 公开时点 | 18 个月 | 申请日 | 检索截止日必须覆盖到该时点前的全部公开 |

### 10.2 业务 SLA（软，可配置）

| SLA | 建议值 | 说明 |
|---|---|---|
| 初步检索 | 1–2 工作日 | 决定是否花钱 |
| 正式检索 | 3–10 工作日 | 与代理所约定的合同义务 |
| 报告评审（企业侧） | 3 工作日 | 超过则阻塞立项会 |
| 结论有效期 | 6 个月 | 超期须复核增量文献 |
| FTO 保鲜期 | 6–12 个月 ⚠ | 行业惯例；新产品上市前必须重跑 |

### 10.3 与 docket 引擎的关系

当前 docket 的 7 条规则（`oa1_response`、`oa_subsequent`、`application_fee`、`substantive_exam_request`、`grant_registration`、`annuity`、`pct_national_entry`）**全部在立案之后**，本节点零覆盖。

**待补三条**：

- `research_stale`（报告满 6 个月未复核）
- `fto_freshness`（FTO 结论到期，提示重跑）
- `priority_window`（自首次申请日起 12 个月，驱动海外布局决策）——这条与 09 PCT 共用

## 11. 边界与失败场景

| # | 场景 | 正确处置 | 现状 |
|---|---|---|---|
| 1 | 发明人说「这个绝对新」，拒绝检索 | 发明人不能以此跳过检索。进不进检索由 00b 初审定；一旦进入，结论不可由发明人出具 | ✅（7 项齐套硬拦） |
| 2 | 交底 1.1 里编了一个公开号 | 正则校验不通过 → 不得计入齐套；同时提示补真实文献 | ⚠ 工作台只查非空 |
| 3 | 检索到 300 篇，只选了 3 篇最相关的 | 报告须记录「筛选规则」与「未选原因」摘要 | ❌ |
| 4 | 三篇 X 类文献把方案完全打掉 | 结论应可置为「暂不建议申请」并触发 02 的 No-Go | ⚠ 自动逻辑永不产负向结论 |
| 5 | 检到自家 5 个月前的会议论文 | 标「宽限期内」，提示声明举证，不得当 X 类 | ❌ |
| 6 | 检到自家 8 个月前的论文 | 结论注明已超宽限，交给 02 做 No-Go（不申请 / 技术秘密 / 防御性公开）。不在本节点禁止申请，不改交底建议 | ❌ |
| 7 | 客户要求「检索报告写好看点」 | 拒绝；`hits_verifiable` 与审计留痕即防线 | ⚠ 依赖制度，无强制 |
| 8 | 代理所提交的报告里 url 全部 404 | 应判不可核验；真实产品需链接存活探测 | ❌ |
| 9 | 方案是实用新型，企业要「可专利性结论」 | 只能出检索意见，正式结论走 CNIPA 评价报告 | ❌ |

**检索质量与交付类：**

| # | 场景 | 正确处置 | 现状 |
|---|---|---|---|
| 10 | 检索截止日早于优先权日 | 报告须标红「存在漏检窗口」 | ❌ |
| 11 | 同一技术两个部门各检索一次 | 命中集应按 pubNo 去重、合并报告 | ❌ |
| 12 | FTO 结论 14 个月后产品才上市 | 上市前必须重跑 FTO | ❌ 无保鲜期字段 |
| 13 | AI 领域，关键对比文件是一篇 arXiv 论文 | NPL 必须进检索范围并单独成层 | ⚠ 只是数据库选项之一 |
| 14 | 涉密项目 | 不走普通检索，走保密专利程序 | ❌ |
| 15 | 检索途中企业换代理所 | 检索式与命中集须可跨所移交 | ❌ 数据在组件 state，不可移交 |
| 16 | 企业只看结论不看命中，直接批准 | 批准前强制展开「结论→命中」对照 | ⚠ 有绑定面板，无强制展开 |

## 12. 指标（验收尺子）

| 指标 | 定义 | 健康区间 | 说明 |
|---|---|---|---|
| 命中可核验率 | 含 pubNo+url 的命中占比 | 100% | 硬指标，非目标值 |
| 空命中提交率 | 无命中仍提交的报告占比 | 0% | 硬闸应使之为 0 |
| 结论-命中绑定率 | 有 binding 的结论条目占比 | 100% | 审计必需 |
| 检索结论与实审一致率 | 实审引用文献落在本报告 X/Y 集中的案件占比 | ≥ 50% ⚠ | 低于此说明检索白做 |
| 检索→申请转化率 | 出具「可申请」结论后实际递交的占比 | 60%–85% ⚠ | 过低说明检索过松或决策另有一套 |
| 单案检索成本 | 外部检索费 + 内部工时折算 | ¥3k–15k ⚠ | 与命中质量做性价比评估 |
| 检索周期中位数 | 接案到报告批准 | ≤ 5 工作日 | 阻塞立项会的主要变量 |
| 报告返工率 | 被 `request_changes` 的比例 | < 15% | 高 → 检索式或模板有问题 |
| FTO 高危件数 | 风险档 = 高的案件数/季 | 越低越好 | 直接对应改设计成本 |
| 同族折叠率 | 折叠掉的重复命中占比 | 20%–60% | 过低说明没做同族归并 |

> 卖产品时优先讲 **「检索结论与实审一致率」**：它把检索质量直接换算成「省下的第二次撰写费 + 半年周期」。其次是**单案检索成本**——企业最容易被「一次检索花了 1.2 万，结果审查员引了三篇它没找到的」说服。

## 13. 产品化切分建议

| 层 | 内容 | 是否可独立交付 |
|---|---|---|
| L1 命中台账 | 多库检索入口、命中列表、pubNo 校验、原文链接 | 是（最低配，可与数据商合作） |
| L2 检索式引擎 | A/B/C 三块构造、布尔式、字段限定、同族折叠、多轮对比 | 是（差异化，检索员愿意付费） |
| L3 三报告分流 | 查新 / 可专利性 / FTO 三模板、三结论口径、按专利类型分流 | 是（护城河，懂法才做得对） |
| L4（已拆出）正式 FTO | 见 [01b](01b-fto.md) / P02b；本节点不再把 FTO 当主卖点 | 是（法务/尽调买单，**独立 SKU**） |
| L5 决策接口 | `SearchReport` → 02 的评分卡输入、`binding` 审计导出 | 依赖 02，但可做 API |

**定价锚点**：按「可专利性报告件数」计价最自然（每份 X 元）；**正式 FTO 单列更高价（P02b）**；或按席位（IP 团队）+ 按 API 调用量（数据商模式）。**不要按「检索次数」计价**——会激励跑量不提质。

**竞品参照系**：

- 数据层：IncoPat / 智慧芽 / Patsnap / Derwent —— 强在数据与语义检索，弱在**中国法结论口径**；
- 流程层：Anaqua / CPA Global —— 强在工作流，检索常是外挂模块；
- 服务层：代理所 —— 强在结论，弱在可复现与留痕。

**空位**：把「数据 + 中国法结论口径 + 可核验留痕」三件事装进同一个对象（`SearchReport`），并让结论能一路传到撰写与无效。市面上三者分离。
