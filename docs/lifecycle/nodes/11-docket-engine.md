## 0. 一句话讲清这个节点

**Docket = 把「法律给的日历」变成「系统里的待办」。** 它监听业务事件（OA 发文、授权通知、申请递交、优先权日），按规则算出到期日，再按四级阶梯把人从「看见」推到「动手」。

它解决的不是「日历提醒」，而是**责任落地**：期限到期前一天，系统必须能回答「谁在负责、现在到哪一步、还差什么材料」。行业里 docketing 是代理所最不容出错的一环——专利运营岗的第一条职业纪律就是「每天开盘先清 docket」。

产品化三条件：

1. **有独立买方**：代理所（交付风险）、企业 IP（资产安全）、专利年费服务商（代缴业务）。
2. **有独立价值**：一次权利丧失的损失通常远高于整套系统的年费；这是最容易算 ROI 的模块。
3. **有独立边界**：输入是「事件 + 日期」，输出是「期限事件 + 升级状态」，不需要撰写、检索、商务任何模块。

## 1. 节点定位与产品边界

### 1.1 在生命周期中的位置

```
立案(00) ──► 递交(03) ──► 实审请求 ──► OA 答复(04) ──► 授权登记 ──► 年费(05) ──► 终止/恢复
               │            │            │              │            │
     application_fee   substantive_   oa1_response   grant_      annuity
                       exam_request   oa_subsequent  registration （12m + 6m 宽限）
                                                           │
    PCT 路径：pct_national_entry（优先权起 30 月 + 2 月宽限）
```

- **无 `StageId`**：横切所有有法定期限的节点。它挂在案件上（`caseId`），不挂在阶段上。
- **与 07 监控的分工**：docket 只管**官方期限**；竞品/侵权/到期预警属 `watch_alert`。`Docket.tsx` 页面明确写「年费办理日程在授权维持工作台；Docket 仅官方期限事件」。
- **页与路由**：workbench `/docket`（`src/pages/Docket.tsx`），支持 `?case=` 过滤与 `?focus=risk` 风险聚焦。
- **命令**：`docketEscalate` / `docketComplete`（`commandNames.ts:22`）。

### 1.2 它是什么 / 不是什么

| 是 | 不是 |

## 2. 角色与权限矩阵

| 角色 | 代码对应 | 能做什么 | 不能做什么 |
|---|---|---|---|
| 企业 IP | `role='enterprise'`, persona `enterprise_ip` | 生成期限、提醒、升级企业、标风险、办结 | 不能伪造回执 |
| 代理所流程岗 | `role='agency'`, persona `agency` | 生成期限、提醒、升级、办结 | 不能替企业确认付款 |
| 发明人 | persona `inventor` | **只读**浏览期限 | 不可提醒/升级/办结/生成 |
| 评审委员 | persona `committee` | **只读**浏览 | 同上 |
| 系统 Agent | `agent-oa` / `agent-annuity` | 读写期限（`write_docket_event` → `fileResponse`） | 不能空回执归档 |

**当前实现的权限真相**：

- 只读判定是两个 persona 的白名单（`src/pages/Docket.tsx:46` 与 `AppContext.tsx:935`），**不是**基于权限点的鉴权。
- 生成与升级都是**内存写**，无审计签名，`escalationActor` 只记 `enterprise_user` / `agency_user`（`AppContext.tsx:963`），不记具体人。
- 「升级到企业 IP」不产生真实站内信/邮件，文案自认「无真推送（演示通道）」（`docketEscalate.ts:99`）。

### 2.1 决策权

> §2 的矩阵回答「谁能改这条期限」，本节回答「凭什么是他说了算」。期限引擎的特殊之处在于：**绝大多数参数不是业务选择，是法律给定值**。把法定值放进「可配置」列表，本身就是一种越权。

**一条硬分割：规则 ≠ 提醒策略**

| 类别 | 内容 | 谁能改 | 改动后是否需要复核 |
|---|---|---|---|
| **法定硬规则** | 期限长度、起算点、宽限期、滞纳金的产生与比例、顺延规则 | 规则维护人（法务 / 流程负责人），且须附法源 | **是**：须双人复核 + 差异说明 |
| **业务策略** | 提前量天数、提醒频次、升级对象、SLA | 流程主管，按 L2 审批 | 否，但须留痕 |
| **个案数据** | 触发日、发文日、文号、案件归属 | 流程岗录入，可更正，须留痕 | 更正须二人（录入 ≠ 更正） |

> **可配置的只有提醒策略。** 如果把「一通答复期」做成可编辑字段，第一次有人为了方便把它改成 6 个月，系统就会在一个合法日期上告诉用户「还早」。

**各类决策的归属**

| 决策 | 建议权 | 决定权 | 否决权 | 边界 |
|---|---|---|---|---|
| 期限规则维护（法条/收费变更时） | 流程主管、代理师 | 法务负责人（硬规则）；流程主管（策略） | 合规 | 硬规则变更须双人复核并在库中保留旧版本，历史事件不回溯重算（见 E1） |
| 宽限期与滞纳金政策 | 流程主管 | 法务 + 财务会签 | 财务 | 宽限期是法定值，不可缩短；滞纳金按官方阶梯，不得自行定价 |
| 升级通知发给谁 | 流程主管 | 企业 IP 负责人 | — | 至少一级发给「人」，不能只发到部门邮箱；A/B 角同时配置 |
| 关闭 / 豁免一条期限 | 流程岗 | 企业 IP 负责人（L2）；涉不可逆后果时 L3 | 合规 | 见下「关闭与豁免」 |
| 延期申请 | 代理师 | 企业 IP 负责人（涉及费用与风险） | — | 延期只能在法定期限内使用，不是内部流程慢的解药 |
| 期限数据错误修正 | 发现人 | 流程主管 + 原录入人以外的第二人 | — | 见下「数据错误」 |
| 多时区 / 节假日顺延规则 | 规则维护人 | 法务（涉外须逐国确认） | — | 顺延规则按官方口径，不按企业内部工作日历 |
| 期限事件生成 | 系统 / 流程岗 | — | — | 生成不进审计目前是缺陷（R11-46） |

**关闭期限的三条铁律**

| 铁律 | 含义 | 为什么 |
|---|---|---|
| 不可由系统自动关闭 | 定时任务只能改 `status`（`due_soon` / `overdue`），不能写 `done` | 自动关闭会让真实逾期消失得无声无息 |
| 必须有凭证 | 办结须挂 `receiptNo` 或官方缴费凭证 | 「已办」和「以为已办」是两种完全不同的状态 |
| 必须具名 + 可解释 | 谁关的、什么时候、依据什么 | 期限是责任，不是待办清单上的勾 |

**关闭 vs 豁免，不是一回事**

| 动作 | 含义 | 前提 | 后果 |
|---|---|---|---|
| 办结（close） | 这件事做完了 | 有回执 / 缴费凭证 | 事件 `done`，不再升级 |
| 豁免（waive） | 这件事本应做，但决定不做 | 有实体决策记录（如 D6 放弃维持） | 事件 `done`，但标记 `waived`，进入资产处置台账 |
| 顺延（defer） | 期限合法延长 | 法定允许 + 已缴延期费 / 已办手续 | 新建 `dueDate` 版本，保留原期限 |

> 三者混用的典型事故：代理所把「客户说先不缴」记成办结，年费台账上看起来干干净净，半年后专利权终止——系统没做错任何计算，只是把「决定不做」记成了「做完了」。

**期限数据错误的责任链**

| 环节 | 责任 | 系统要求 |
|---|---|---|
| 录入 | 录入人 | 录入人具名 + 录入时间 + 来源文号 |
| 复核 | 第二人（高风险规则强制） | 复核标记；未复核的事件在列表中可见 |
| 更正 | 更正人（不得为原录入人） | 原值保留，新值覆盖需理由；两条都进审计 |
| 事故归因 | 流程主管 | 错一个期限要能回答「哪一步漏了」 |

| ID | 规则 | 现状 |
|---|---|---|
| R11-39 | 期限长度、起算点、宽限期、顺延规则属法定硬规则，不得由租户级业务配置覆盖；租户只能配置提醒策略 | ❌ 规则为全局常量，但无「不可配置」的显式约束 |
| R11-40 | 硬规则变更须法务复核 + 双人签署，旧版本保留可查，且变更生效日之前的在办事件不自动重算 | ❌ 无版本号（R11-10） |
| R11-41 | 办结（`done`）必须附凭证（`receiptNo` 或官方缴费凭证）；无凭证不得办结 | ❌ `complete` 不校验（§6.4-7） |
| R11-42 | `done` 只能由具名的人触发，不得由定时任务 / Agent 自动写入 | ⚠ 目前不会，但无硬约束 |
| R11-43 | 豁免（决定不做）须有实体决策记录（如 D6）+ 具名批准人，且与办结在数据上可区分 | ❌ 无 `waived` 语义 |
| R11-44 | 期限事件生成必须计入审计（谁、何时、按哪条规则、哪个触发日） | ❌ 无 `CommandName`（§9） |
| R11-45 | 期限数据更正不得由原录入人独立完成，须第二人确认；原值永久保留 | ❌ 无更正机制 |
| R11-46 | 升级通知的接收人必须是具体人（含 A/B 角），不得只指向部门或角色占位 | ❌ `escalationActor` 仅两种粗粒度 |
| R11-47 | 延期决定由企业 IP 负责人作出；延期不得用于掩盖内部排产延误，延期率纳入复盘 | ❌ 无延期对象（§10.3-3） |
| R11-48 | 多时区事件的「今天」以业务主体所在时区的服务端时间为准；跨时区期限各自标注时区 | ❌ 全用客户端 `new Date()` |
| R11-49 | 节假日顺延规则按官方口径维护，企业内部工作日历不得作为顺延依据 | ❌ 未建模（§5.7-2） |

### 3.3 升级对象 `DocketEscalationLevel`

`none → reminded → escalated_enterprise → at_risk`（`types/index.ts:451`）。四级严格**单向递进**，不允许跳跃或回退（`docketEscalate.ts:44` 的 `ladderNextActions` 每步只暴露下一步 + 办结）。

### 3.4 四个状态 vs 四个升级级 —— 别混

| 维度 | 回答什么 | 取值 | 谁写 |
|---|---|---|---|
| `status` | 时间上到哪了 | `upcoming` / `due_soon` / `overdue` / `done` | 生成时定 / 办结时改 |
| `escalationLevel` | 人的动作到哪了 | `none` / `reminded` / `escalated_enterprise` / `at_risk` | 人工推进 |

> 关键：**两者独立**。`overdue` 且 `none` 是常态（刚逾期还没人动）；`due_soon` 且 `at_risk` 也合法（提前标风险）。`status` 不由日期自动推进——当前没有定时重算任务，`due_soon/overdue` 主要靠 seed 写死（§14 差距 1）。

### 4.7 例外情形

期限引擎里没有「通融一下」这回事：法定期限不因内部原因延长。能作为例外的，只有两种——**法律本身给的出口**，和**官方事实与系统记录不一致**。前者应做成规则，后者应做成更正记录。

| # | 例外 | 例外条件 | 谁批准 | 风险 | 留痕 |
|---|---|---|---|---|---|
| E1 | 法条 / 收费标准变更导致规则需更新 | 官方发布施行日期明确的新规 | 法务 + 流程主管双签 | 新旧规则混用，同一批事件一半按新口径一半按旧口径 | 必留：变更依据 + 施行日 + 影响事件清单 + 是否重算的决定 |
| E2 | 官方系统故障导致无法按时提交 | 电子申请系统停机、缴费通道不可用，且有停机公告或提交失败截图 | 代理所负责人 + 企业 IP 负责人 | 故障期间是否构成「正当理由」由官方认定，不由双方认定 | 必留：故障时段证据 + 尝试记录 + 恢复后第一时间补交 |
| E3 | 不可抗力 | 灾害、疫情管控、通信中断等，客观上无法操作 | 企业 IP 负责人 + 法务 | 「不可抗力」认定门槛高，日常延误不能援引 | 必留：事件说明 + 证明材料 + 恢复权利/延期请求及官方答复 |
| E4 | 节假日顺延致到期日与系统计算不符 | 期限末日落于法定节假日或官方公布的非工作日 | 系统按规则自动，无需人批 | 系统未建模时长期偏差；跨境时各国节假日不同 | 必留：原到期日 + 顺延后到期日 + 依据（规则版本） |
| E5 | 期限计算争议（起算日认定） | 发文日与送达日不一致、电子送达时间戳存疑、是否加邮路日存在不同理解 | 代理师建议，企业 IP 负责人决定；涉外按当地代理意见 | 起算日错一天即全盘错；争议期间仍须按较早日期准备 | 必留：起算日认定意见 + 依据 + 最终采用日 + 风险声明 |
| E6 | 系统时间错误 | 客户端时间被改、跨时区显示错、服务端时钟漂移 | 系统管理员 + 流程主管 | 「今天」判断错会导致 `overdue` 误判，进而误升级或漏升级 | 必留：错误时段 + 受影响事件清单 + 重算结果 |

**例外里的三条红线**（任何批准都不能突破）：

| 红线 | 原因 |
|---|---|
| 倒填触发日 / 发文日 | 伪造期限起点，等于伪造程序事实 |
| 用「已缴」备注代替缴费凭证 | 期限是否满足是客观事实，不是备注 |
| 以内部审批未完成主张顺延 | 内部流程不是法定理由 |

**例外与「正常功能」的边界**：

| 情形 | 属于 | 处理位置 |
|---|---|---|
| 延期缴费 / 延期答复 | 正常功能（法定救济） | 规则表 + 延期对象，非例外 |
| 恢复权利 | 正常功能（法定救济） | 独立流程，非例外 |
| 节假日顺延 | 正常功能（计算规则） | `computeDueDate` 内，非例外 |
| 官方系统故障 | **例外** | E2，逐案留痕 |
| 起算日争议 | **例外** | E5，逐案认定 |

> 把前三项做成「特批」是最常见的建模错误：它们本来就是规则，做成例外会让每一次合规操作都看起来像破例，例外统计随即失效。

| ID | 规则 | 现状 |
|---|---|---|
| R11-50 | 规则变更须区分「影响在办事件」与「仅影响新生事件」，并逐条记录重算决定 | ❌ |
| R11-51 | 官方系统故障不可由任一方单方认定，须双方共同确认并保存客观证据 | ❌ |
| R11-52 | 不可抗力主张须在恢复后第一时间启动法定救济（延期 / 恢复权利），不得只做内部备注 | ❌ |
| R11-53 | 起算日存在争议时，按「较早日期」准备并在系统中同时记录争议日期与采用的日期 | ❌ |
| R11-54 | 系统时间一律以服务端为准；客户端时间仅作展示，不得参与 `due_soon` / `overdue` 判定 | ❌ |
| R11-55 | 例外的批准人、理由、有效期、受影响事件必须可统计；红线项不得提供例外入口 | ❌ |

### 4.8 规则冲突与裁决

期限引擎的冲突有一个共同点：**两边看起来都「为客户好」**，但一边会牺牲正确性。裁决的关键不是选哪边，而是把「正确」与「体验」分到两个不同的层去满足。

| # | 冲突 | 一方 | 另一方 | 裁决 | 裁决人 |
|---|---|---|---|---|---|
| C1 | 提醒太频繁 vs 被忽略 | 合规（宁可多提醒） | 体验（提醒疲劳后全部无视） | **按剩余时间分层收敛**：提前量只保留 3–4 个节点（如提前 60/30/14/7 日 ⚠ 可配），中间靠看板而非通知；`at_risk` 事件强制每日可见 | 流程主管定频次，企业 IP 负责人定接收人 |
| C2 | 自动化 vs 人工确认 | 效率（自动改状态、自动升级） | 责任（谁确认的） | **状态可自动，责任不可自动**：`due_soon` / `overdue` 由系统算；`done`、豁免、延期必须人做。升级可自动推进到 `reminded`，进入 `escalated_enterprise` 须人确认 | 系统 + 企业 IP 负责人 |
| C3 | 统一规则 vs 个案特殊 | 规则库（一套口径） | 个案（某客户某案确有特殊安排） | **法定部分不许特殊，策略部分允许按案件覆盖**：期限长度不可覆盖；提前量、接收人、提醒方式可按案件配置，且配置本身留痕 | 流程主管 |
| C4 | 提前量长 vs 客户反感 | 风控（越早越好） | 客户（一年前就催年费） | **内部提前量 ≠ 对外触达**：内部可提前 90 日生成提醒与待办，对外通知按客户偏好收敛到 30 日内；两者分开配置 | 企业 IP 负责人 |

**裁决顺序（无法消解时，自上而下）**：

| 序 | 原则 | 含义 |
|---|---|---|
| 1 | 法定硬规则优先 | 期限长度、起算、宽限、顺延不可为体验让路 |
| 2 | 正确性优先于自动化程度 | 宁可少自动一步，不可让系统替人做责任动作 |
| 3 | 不可逆优先 | 近到期、涉终止/视为撤回的事件，先于所有可逆事项处理 |
| 4 | 单一真相优先 | 三套阈值必须收敛为一套；冲突时以「最保守的到期日」为准 |
| 5 | 分层满足 | 内部风控与对外体验分属不同层，不在一处取舍 |

| ID | 规则 | 现状 |
|---|---|---|
| R11-56 | 提醒节点数须收敛为可配置的少量节点，禁止「越临近越频繁」的无上限叠加 | ⚠ 三套阈值并存（§4.6） |
| R11-57 | 状态推进可自动，`done` / 豁免 / 延期不可自动；自动升级最多推进到 `reminded` | ❌ 全人工（§6.4-4） |
| R11-58 | 案件级覆盖只允许作用于策略参数（提前量 / 接收人 / 提醒方式），不得作用于期限长度 | ❌ |
| R11-59 | 内部提前量与对外触达时间须分别配置，不得用同一个值 | ❌ |
| R11-60 | 同一事件存在多个候选到期日时，一律按最早日期建单并注明差异 | ❌ |

## 5. 法律底座 / 行业规则

以下逐条给「规则要点 / 产品落点 / 失效后果」。**条号与具体月数均标 ⚠，须按当期文本复核**；未核实的不写条号。

### 5.1 审查意见答复期限（OA 答复）

**规则**：实质审查中，每次审查意见通知书都会**指定答复期限**（一通通常 4 个月，后续通常 2 个月，⚠ 以通知书载明为准，来自《专利审查指南》实审程序，而非细则固定条文）。逾期不答复，申请**视为撤回**。可在期限内请求**延期**并缴纳延期费（⚠ 月数与费用按当期规定）。

**产品落点**：`oa1_response` / `oa_subsequent` 两条规则；`linkedHandoffKey = prosecution_response` 把期限与答复产物钉在一起；未答复时该产物停在 `drafting`。

**失效后果**：视为撤回 = 申请日作废，同一技术再申请会被自己的公开（18 个月公开后）破坏新颖性。这是**不可逆**的。

### 5.2 申请费与实审请求

**规则**：申请费须自申请日起规定期限内缴纳（实务常见 2 个月，或收到受理通知书后 15 日 ⚠）；发明专利申请须自**申请日（有优先权的自最早优先权日）起 3 年内**提出实质审查请求并缴费，否则**视为撤回**（《专利法》第三十五条 ⚠ 条号需核）。

**产品落点**：`application_fee`（2 个月 + 15 日两口径）与 `substantive_exam_request`（36 个月）。后者从**优先权日**起算，是一票否决型期限。

**失效后果**：实审请求逾期 = 申请死亡，且不能通过"补交"救活（只能走恢复权利，需正当理由）。

### 5.3 授权登记

**规则**：收到授予专利权通知后，须在规定期限内办理登记手续（缴费），逾期**视为放弃**取得专利权（⚠ 具体期限以通知书为准，规则表取 2 个月）。

**产品落点**：`grant_registration`；与年费第 1 年绑定（登记费 + 首年年费）。

**失效后果**：视为放弃后需走恢复程序，逾期不恢复则权利彻底丧失，且该技术方案已公开。

### 5.4 年费、滞纳与终止

**规则**：年费应于**申请日周年**前缴纳；未缴或不足的，可在**届满之日起 6 个月内补缴**并缴**滞纳金**（按逾期时长阶梯加收，⚠ 比例与上限以《专利收费办法》为准）。超过 6 个月仍未缴足，**专利权终止**。终止后可在收到终止通知后规定期限内请求**恢复权利**（⚠ 期限与条件以细则为准）。

**产品落点**：`annuity` 规则 `months: 12 / graceMonths: 6`。年费日历 `generateAnnuitySchedule` 生成年度 rows。

**失效后果**：终止 = 权利进入公有领域，不可复活（恢复窗口过后）。这是企业 IP 资产表上最常见的"无声损失"。

**⚠ 2024 年新增**：开放许可实施期间年费减免 15%，且各项减免**不得重复享受**、可选最优惠一项（CNIPA 2024-08-06 公告，依据财税〔2024〕23 号）。另有"专利权期限补偿"请求费 200 元/件、补偿期年费 8000 元/件·年。系统未建模。

### 5.5 PCT 国家阶段进入

**规则**：PCT 国际申请进入中国国家阶段，期限通常为**优先权日起 30 个月**（部分国家 31/32 个月，⚠ 按受理局与指定局规定），可缴宽限费延长（中国实务常见 2 个月宽限 ⚠）。

**产品落点**：`pct_national_entry` 单条规则。**这与真实业务差距最大**：多国进入是「一国一行」，每国期限、费用、语言、代理都不同。

**失效后果**：错过进入期限 = 该国无权利，且通常不可恢复。

### 5.6 恢复权利（当前完全未建模）

**规则**：因不可抗力或其他正当理由延误期限导致权利丧失的，可在规定期限内请求恢复权利并缴费（⚠ 期限与理由标准以细则为准；2023 修订后部分情形的起算点有调整）。

**产品落点**：**无**。系统没有 `restore` 类事件，也没有「已终止」状态。

**失效后果**：不是"没提醒"，而是"提醒了但没给救活路径"，用户会以为无解。

### 5.7 期限计算的两条工程铁律（非法条，但属行业硬约束）

1. **期限按「发文日 + 月数」算，且电子申请不再加邮路日**（2023 细则施行后，电子申请通知的答复期限自发文日起算 ⚠ 需按当期规则复核）。系统 `addMonths` 直接加月，未处理"月末对齐"（如 1 月 31 日 + 1 月 → 3 月 3 日，JS `Date` 行为）。
2. **法定节假日顺延**：期限最后一日为法定节假日的，顺延至节假日后第一个工作日（中国实务通行）。系统**未建模**。

## 6. 状态机

### 6.1 事件状态

```
       generate            （日期推进，当前未自动）
upcoming ──────────────────────────────► due_soon ──────────► overdue
   │                                        │                   │
   └────────────── complete ────────────────┴───────────────────┘
                          ▼
                        done（终态）
```

### 6.2 升级阶梯（与状态正交）

```
none ──remind──► reminded ──escalate_enterprise──► escalated_enterprise ──mark_at_risk──► at_risk
  │                  │                                  │                                  │
  └──────────────────┴──────────── complete ────────────┴──────────────────────────────────┘
                                        ▼
                                   done + 消待办
```

### 6.3 迁移表

| 维度 | 当前 | 可迁往 | 谁做 | 业务含义 | 出口条件 |
|---|---|---|---|---|---|
| status | `upcoming` | `due_soon` | 系统（应自动） | 进入提前量窗口 | 距今 ≤ 阈值 |
| status | `due_soon` | `overdue` | 系统（应自动） | 已过期 | 今天 > dueDate |
| status | 任意非 done | `done` | 企业/代理 | 办结 | 有回执或确认 |
| escalation | `none` | `reminded` | 企业/代理 | 已记录提醒 | status ∈ {due_soon, overdue} |
| escalation | `reminded` | `escalated_enterprise` | 企业/代理 | 责任上移企业 IP | 同上 |
| escalation | `escalated_enterprise` | `at_risk` | 企业/代理 | 标风险 + 案件 `risk='高'` | 同上 |
| escalation | `at_risk` | — | — | 终点 | — |

### 6.4 当前实现的偏差

1. **`status` 不会随时间自动变化**：没有定时任务，`due_soon` / `overdue` 靠 seed 写死（`docketRules.ts:162`）。今天日期推过 `dueDate`，事件仍显示 `upcoming`。
2. **`graceMonths` 只存不用**：`computeDueDate` 完全不读它（`docketRules.ts:120`），宽限期在系统里不存在。
3. **`slaDefaultDays` 无消费方**：全库只有定义处出现。
4. **升级不自动**：四级阶梯全靠人工点击，与「自动升级」的产品承诺相反。
5. **`escalationActor` 只有两种值**（`enterprise_user` / `agency_user`），无法回答"是谁"。
6. **`at_risk` 只改企业侧待办**，代理所侧看不到（`docketEscalate.ts:155` 固定 `assignee: 'enterprise'`）。
7. **`complete` 不校验回执**：`docketEscalate.ts:74` 的办结分支不要求 `receiptNo`，与 05 维持「禁静默假回执归档」的 guardrail 矛盾。

## 7. 闸门与条件（代码对齐）

Docket 自身没有独立 guardrail 模块；它的闸门分散在三处：

| 闸门 / 条件 | 触发条件 | 文案 | 代码位置 |
|---|---|---|---|
| Persona 只读 | `inventor` / `committee` 执行生成/升级/办结 | 「当前 Persona 只读 · 不可生成官方期限」 | `Docket.tsx:48` / `AppContext.tsx:935` |
| 已办结不可升级 | `status === 'done'` 且动作 ≠ complete | 「已办结，无法升级」 | `AppContext.tsx:946` |
| 阶梯越级 | 动作不在 `ladderNextActions` | 「当前阶梯为「X」，不可执行 Y」 | `AppContext.tsx:950` |
| 非 due_soon/overdue | 状态为 `upcoming` 或 `done` 却要升级 | 「仅 overdue / due_soon 可走升级阶梯」 | `AppContext.tsx:958` |
| 事件不存在 | 事件 id 找不到 | 「期限事件不存在」 | `AppContext.tsx:944` |
| 发票阻塞（间接） | 代理有逾期发票时 `file` 被挡 | 「存在逾期发票，请先结清」 | `guardrails.ts:274` |

**唯一入口原则**：期限状态的所有写操作必须走 `escalateDocketEvent` / `addDocketEvent`，页面不得直接 `setDocketEvents`。当前 `transitionHandoff` 里的 docket 回写是**直接 `setDocketEvents`**（`AppContext.tsx:1249`），已违反该原则。

## 8. 步骤序列 / 工作流

### 8.1 正常办结流程

| # | 步骤 | 谁做 | 耗时 | 产出 | 失败回退 |

## 10. 期限与 SLA

### 10.1 法定/硬期限（规则表所覆盖）

| 规则 | 长度 | 触发 | 宽限 | 官费提示（示意 ⚠） | 法源（须复核） |
|---|---|---|---|---|---|
| `oa1_response` | 4 个月 | 一通发文日 | 延期费按月累进 | 延期请求费 ¥300/600/900 ⚠ | 审查指南·指定期限 |
| `oa_subsequent` | 2 个月 | 后续发文日 | 同上 | 同上 ⚠ | 同上 |
| `application_fee` | 2 个月 / 15 日 | 申请日 / 受理通知 | 无 | 申请费 ¥900 + 公布印刷 ¥50 ⚠ | 实施细则 ⚠ |
| `substantive_exam_request` | 36 个月 | 优先权日 | 无 | 实审费 ¥2,500 ⚠ | 专利法第三十五条 ⚠ |
| `grant_registration` | 2 个月 | 授权登记通知 | 无 | 登记费 + 印花税 + 当年年费 ⚠ | 实施细则 ⚠ |

| `pct_national_entry` | 30 个月 | 优先权日 | 2 个月 | 申请费 + 附加费 + 实审费 ⚠ | PCT 细则 / 中国国家阶段 |

### 10.2 业务 SLA（软）

| SLA | 建议 | 现状 |
|---|---|---|
| 新事件生成延迟（收到通知 → 录入） | < 1 工作日 | ❌ 无度量 |
| `due_soon` 首次提醒 | 到期前 30 日 | ⚠ 三套阈值并存 |

| 标风险 | 到期前 7 日 | ❌ 人工 |
| 年费代缴确认 | 到期前 15 日 | ❌ |

### 10.3 缺口（本节点最重要的部分）

| # | 缺口 | 说明 |
|---|---|---|
| 1 | **交底阶段无 docket** | 00 交底的 `riskDate`（新颖性宽限起点）、部门审核 SLA、交底包补齐 SLA 全部无期限；docket 从立案后才开始（见 00 §12.4） |
| 2 | **多国期限并发未建模** | `pct_national_entry` 是单条规则，无法表达「US 30 月 / EP 31 月 / JP 30 月 + 翻译期限」的多行矩阵 |
| 3 | **延期（延长缴费/答复期）未建模** | 延期费只在 `officialFeeHint` 文案里；没有「延长期限」对象，`dueDate` 改了就丢失原期限证据 |

| 6 | **分割申请 / 优先权期限 / 18 个月公开**未建模 | 三条常见期限规则缺失 |
| 7 | **滞纳金不计入金额** | 只有文案，`amount` 仍是年费本身 |
| 8 | **官方不可逆锚点未登记** | 受理日/公开日/授权日无字段，只散在 timeline 文本里 |

| # | 场景 | 正确处置 | 现状 |

| 11 | 企业 IP 离职，期限无人接手 | 升级到部门负责人 | ❌ 阶梯终点是企业 IP |

## 12. 指标（验收尺子）

| 指标 | 定义 | 健康区间 | 说明 |
|---|---|---|---|
| 期限录入及时率 | 收到通知 1 工作日内录入的比例 | > 98% | 最前置的防线 |
| 逾期事件数 | 全年 `overdue` 事件计数 | 0（目标） | 任何非零都要复盘 |
| 提前提醒覆盖率 | `due_soon` 时已有 `reminded` 的比例 | > 90% | 反映流程是否真的在跑 |
| 升级及时率 | 到期前 14 日完成 `escalated_enterprise` 的比例 | > 85% | |
| 权利丧失数 | 因期限导致视为撤回/终止的案数 | 0 | **能直接换算成钱** |
| 年费按时缴纳率 | 到期前缴纳的比例 | > 95% | 减少滞纳金 |
| 滞纳金总额 | 年度滞纳金合计 | 越低越好 | 直接成本 |
| 延期使用率 | 使用延期的期限数 / 总期限数 | 5%–15% | 过高说明排产有问题 |
| 规则覆盖率 | 有 docket 规则的期限类型 / 实际发生类型 | 100% | 当前 7/N |

> 能换算成钱的：**权利丧失数 × 单件资产重置成本**（重新研发 + 再申请 + 市场窗口），以及**滞纳金总额**。

## 13. 产品化切分建议

| 层 | 内容 | 是否可独立交付 |
|---|---|---|
| L1 规则层 | 七条规则 + 到期日计算 | 是（可嵌入任何案管系统） |
| L2 日历层 | 列表/月历/风险聚焦 | 是（最低配产品） |
| L3 升级层 | 四级阶梯 + 待办联动 | 是（差异化） |
| L4 年费层 | 全周期年费日历 + 减缴 + 滞纳 | 是（年费代缴服务商刚需） |
| L5 多国层 | 国家矩阵 + 各国费用 | 是（涉外代理所，单价最高） |
| L6 自动层 | 官文解析 + 自动建单 + 自动升级 | 依赖外部数据源 |

**定价锚点**：按「在管专利件数 × 年」最自然；年费代缴场景可按「代缴件数 × 每件服务费」。

**竞品参照系**：CPA Global / Dennemeyer 的 docketing 强在多国与官文，弱在中国本地化（减缴、恢复、节假日顺延）；国内代理机构系统强在官文收发，弱在**企业侧可见性与升级**。**「中国法本地化 + 企业侧升级」是空位。**

| # | 差距 | 严重度 | 影响 |
|---|---|---|---|
| 1 | `status` 不随时间自动推进 | **高** | 系统会"忘记"已经逾期 |
| 2 | `graceMonths` 不参与计算 | **高** | 宽限期事实上不存在 |

| 9 | `slaDefaultDays` 无消费方 | 低 | 死字段 |
| 10 | 无节假日顺延 | **高** | 到期日系统性偏差 |
| 11 | 无延期对象 | **高** | 无法合法延长且保留证据 |
| 12 | 无恢复权利 | **高** | 丧失后无救活路径 |
| 13 | 无多国矩阵 | **高** | 涉外业务不可用 |
| 14 | 无交底阶段期限 | 中 | 前端 SLA 空白 |
| 15 | `complete` 不校验回执 | 中 | 假办结 |
| 16 | 生成期限不进审计 | 中 | 无法追责 |
| 17 | 全客户端时间 | 中 | 时区/改时间即失效 |
| 18 | 无官方锚点字段 | 中 | 官方态只能写在文本里 |

**优先补的三件事**：

1. **状态自动重算 + 自动升级**（差距 1、3）——一天两次的定时任务即可，收益最大。
2. **`file` 回写映射修正**（差距 4、5）——改为复用 `Docket.tsx:129` 的映射与 `computeDueDate`。
3. **宽限与滞纳三态**（差距 2、6）——`annuity` 扩成「到期 → 宽限（含滞纳金）→ 终止」，直接对应 05 维持的核心风险。

## 15. 术语表
