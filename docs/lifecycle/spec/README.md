# 机器可读层（spec）

> **这一层是生成物，不要手改。** 手写源是 `docs/lifecycle/nodes/*.md`。
>
> 目的：让同一套业务逻辑既给人读（markdown），也给模型和工具读（本目录）。
> 重跑：`npm run spec:lifecycle`；只校验不写盘：`npm run spec:lifecycle:check`。

---

## 1. 为什么是「抽取」而不是「双写」

两条路可选：

| 方案 | 做法 | 问题 |
|---|---|---|
| 双写 | 人写 md，再手写一份 yaml/json | 两份必然漂移，且没人维护第二份 |
| **抽取** | md 是唯一事实源，脚本生成 spec | 格式受约束，但**永远不会不一致** |

选了抽取。代价是 markdown 的表格格式必须稳定——所以 `_TEMPLATE.md` 规定了规则表必须是 `| ID | 规则 | 现状 |`。格式一旦破坏，`npm run spec:lifecycle:check` 会报错。

## 2. 产物

| 文件 | 内容 | 给谁用 |
|---|---|---|
| `nodes.json` | 20 个节点的元信息（id / 标题 / stage / 决策点 / 规则数） | 导航、索引 |
| `rules.json` | **1026 条规则**的完整结构化数据 | 模型、校验工具 |
| `decisions.json` | **117 条决策权**（决策 / 建议 / 决定 / 否决 / 知情 / 级别） | 权限设计、审计 |
| `schemas.json` | 文档中 TS 代码块里的对象名清单 | 数据建模参考 |
| `AGENT-CONTEXT.md` | 一页式紧凑摘要（规则编号 + 一句话） | 塞进模型上下文 |
| `AGENT-CONTEXT.md` | 同上 | 同上 |

### 2.1 `rules.json` 单条结构

```json
{
  "id": "R05-57",
  "node": "05-maintenance",
  "section": "2.1 决策权",
  "category": "B-决策权",
  "statement": "批量放弃按件数与年化维持成本孰高定档，B 档及以上须法务 + 财务联签",
  "status": "missing",
  "statusNote": "无批量分级",
  "suggested": "可选",
  "note": "可选",
  "source": "docs/lifecycle/nodes/05-maintenance.md:203"
}
```

关键字段：

- **`status`**：`done` / `partial` / `missing` / `unknown`，由「现状」列的图标推断。**这是原型的实现状态，不是业务要求**——业务要求看 `statement`。
- **`category`**：17 类。规则不是一类东西（见 §4），分类决定它应该被硬编码还是可配置。
- **`source`**：精确到行号，可回溯。

## 4. 规则分类为什么重要

同一份文档里，规则的**性质完全不同**，混在一起写就会写出「什么都提一句、什么都做不了」的规格。

| 类别 | 可变性 | 实现方式 | 例 |
|---|---|---|---|
| A-法定/程序 | 极低（修法才变） | **硬编码 + 不可配置** | 答复期限 4 个月 |
| B-决策权 | 中（组织架构） | 可配置的权限矩阵 | 谁批预算 |
| C-例外 | 低 | 特批通道 + 强制留痕 | 紧急立项 |
| D-冲突裁决 | 低 | 优先级表 | 期限优先于质量 |
| E-质量 | 中 | 可开关的校验 | 齐套检查 |
| N-商务/计费 | 高 | 可配置 | 报价、发票 |
| Q-领域规则 | 中 | 需专家复核 | 等同判定 |

**产品含义**：A 类做成配置项就是事故（客户可以把答复期改成 90 天）；Q 类做成硬编码就是僵化。这份分类是设计配置中心的基础。

## 5. 这一层现在能做什么、不能做什么

### 能用

- **模型上下文**：`AGENT-CONTEXT.md` 约 1.1k 行，可以整篇塞进上下文，让 AI 理解业务规则
- **一致性校验**：规则编号唯一性、格式合规性（`--check` 会报错）
- **覆盖率分析**：某个产品覆盖了哪些规则、哪些还没落地
- **决策权查询**：「放弃专利谁有权批」可以直接从 `decisions.json` 查到

### 不能用

- **直接执行**：规则是自然语言，没有形式化为 `{前件, 动作}`。要做运行时校验，需要人工再转一层
- **替代人读文档**：丢掉了「为什么这条重要」「不这么做会怎样」的因果，而这是文档最有价值的部分

### 下一步（如果要往「机器执行」走）

需要的是**第三层**：把每条规则拆成可判定条件。

```
rules.json（现在）      →  { id, statement, category }
         ↓ 人工/半自动
checks/*.yaml（未来）   →  { id, when: {...}, assert: {...}, blocker: "..." }
```

**但这一步不该现在做**。理由：规则还没稳定（这次就改了 400 多条），过早形式化会产生大量返工。等产品逻辑定下来、哪些规则真的要进代码再转。

## 6. 维护

| 场景 | 做法 |
|---|---|
| 改业务规则 | 只改 `nodes/*.md`，然后 `npm run spec:lifecycle` |
| 新增节点 | 新建 `nodes/NN-xxx.md`，按 `_TEMPLATE.md` 写规则表，重跑 |
| CI 校验 | 加 `npm run spec:lifecycle:check`，能挡住格式破坏和编号重复 |
| 分类不准 | 改 `scripts/lifecycle-spec.mjs` 的 `CATEGORY_RULES`，重跑 |

**禁止**：直接编辑 `spec/*.json` 或 `AGENT-CONTEXT.md`。下次生成会覆盖。
