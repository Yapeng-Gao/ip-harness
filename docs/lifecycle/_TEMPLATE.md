# 节点文档模板（产品级规格 · 17 节）

> **所有节点文档必须按此结构写。** 样板：[00-inventor-disclosure.md](nodes/00-inventor-disclosure.md)。
> 目的：读者读完后能独立设计这个节点的产品、写它的接口、给客户讲清它为什么值钱。
>
> 与旧「8 节地图版」的区别：
> - 地图版回答「代码里有什么」；产品级回答「业务上应该是什么、为什么、怎么算合格」。
> - 地图版是描述；产品级是**规格**——含字段级 schema、编号规则、失败场景、指标、差距表。
> - 地图版写给读代码的人；产品级写给**要拿它做产品的人**（含实习生）。

---

## 结构（17 节，顺序固定）

### 0. 一句话讲清这个节点
用 2–3 句话说清：它是什么、它解决谁的什么问题、为什么它能独立成产品。
然后是「产品化三条件」：有独立买方 / 有独立价值 / 有独立边界。

### 1. 节点定位与产品边界
- 在生命周期中的位置（画 ASCII 链路图）
- StageId / 路由 / 壳 / 产物键（代码口径）
- **是 / 不是** 对照表（最容易误解的边界）
- 上下游契约表（方向 / 对象 / 契约）
- **独立产品的形态**：产品名建议 + 模块拆解表 + 不做什么

### 2. 角色与权限矩阵
表格：角色 / 代码对应 / 能做什么 / 不能做什么。
然后单独写「当前实现的权限真相」——哪些是真鉴权、哪些是角色芯片、哪些是只读。

### 3. 业务对象（字段级）
每个对象一张表：字段 / 类型 / 必填 / 说明。
必须写明权威源文件路径。
若有多个对象容易混，**单独一节讲清区别**（参考 00 的「三层，别混」）。

### 4. 业务规则（编号）
按类别分组，编号 `R<节点号>-<两位序号>`，例如 `R04-12`。
每条规则一行，表格三列：ID / 规则 / 现状（✅ 已实现 / ⚠ 部分 / ❌ 未实现）。
类别建议：核心判定 / 齐套校验 / 合规 / 时限 / 写回 / 权限。

**规则必须可测。** 「应保证质量」不是规则；「6 项齐套全为真才可 approve」是规则。

### 5. 法律底座 / 行业规则
这是产品护城河。逐条写：
- **规则**（法条号 + 原文要点）
- **产品落点**（系统里体现为什么）
- **失效后果**（不这么做会怎样）

必须标注 ⚠ 当金额/比例可能随政策变动时。
如果该节点没有强法律约束（如纯商务线），写「行业惯例」并说明来源。

### 6. 状态机
- ASCII 状态图
- 合法迁移表（当前态 / 可迁往 / 谁做 / 业务含义 / 出口条件）
- **当前实现的偏差**：代码与设计不一致的地方，逐条点名

### 7. 闸门与条件（代码对齐）
表格：闸门/blocker 码 / 触发条件 / 文案 / 代码位置（文件:行）。
必须写「唯一入口」原则：任何 UI 都要过 `evaluateGuardrails`。

### 8. 步骤序列 / 工作流
逐步写：步骤 / 谁做 / 耗时 / 产出 / 失败回退。
若是 wizard，标出每步的完成条件。

### 9. 写回与命令
表格：动作 / CommandName / 写入对象 / 是否跨口。
跨口的部分要写清同步策略（见 crossPortStore）。

### 10. 期限与 SLA
- **法定/硬期限**（有法律后果的）
- **业务 SLA**（软、可配置，给建议值）
- 与 docket 引擎的关系（哪些已覆盖、哪些缺）

### 11. 边界与失败场景
表格 15 条左右：# / 场景 / 正确处置 / 现状。
场景要具体（「发明人下月离职」「交底里编了个公开号」），不要抽象（「异常情况」）。

### 12. 指标（验收尺子）
表格：指标 / 定义 / 健康区间 / 说明。
必须有一两个「能换算成钱」的指标。

### 13. 产品化切分建议
分层表：层 / 内容 / 是否可独立交付。
加定价锚点建议 + 竞品参照系（说明空位在哪）。

### 14. 现状差距表
表格：# / 差距 / 严重度 / 影响。
最后给「优先补的三件事」并说明理由（投入产出比）。

### 15. 术语表
表格：术语 / 含义。只收本节点特有或易混的。

### 16. 来源
法律条文官方链接 + 行业实务来源。**不得编造 URL。**

## 写作纪律

1. **以代码为准**：文档与代码冲突时，以代码为事实，并在「现状差距」里写清差异。不要凭想象描述代码。
2. **不编造**：法条条号、金额、比例必须来自检索到的一手/权威来源。查不到就写「需核实」并标 ⚠，绝不猜。
3. **可测**：规则要能被写成测试用例。
4. **讲因果**：「缺失后果」列必须写清不这样做会发生什么，而不是「不合规」。
5. **中文**，术语首次出现给英文/代码名。
6. 表格优先于长段落。单个表格不超过 12 行，超了拆。
7. 代码引用用 `文件:行号` 格式。
8. 不写「我们」「本系统」这类第一人称；用「系统」「产品」。

## 最低篇幅

产品级节点的正文（不含表格边框）建议 500–700 行。
横切节点（10–13）可略短，但不得少于 350 行。
**宁可深而准，不要全而浅。**
