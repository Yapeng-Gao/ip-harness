# 产品逻辑（Product Logic）

> **这份文档回答：把上面那套业务逻辑，做成什么产品、卖给谁、怎么收钱、先做哪个。**
> 上游依据：[business-spine.md](business-spine.md)（业务总纲）与 nodes/00–24（节点业务规格）。
> **本文不描述代码实现**。原型现状只用于评估迁移成本。
>
> 建立日期：2026-10-20。

---

## 0. 这份文档要解决什么问题

业务逻辑回答「这件事应该怎么做」，产品逻辑回答「谁愿意为它付钱」。

两者之间有一个常见的断裂：**业务上正确的事，商业上未必成立**。比如「交底书把要解决的问题、方案、效果说清」业务上绝对正确，但如果只做一个表单工具，客户会问「这不就是 Word 模板吗」。

所以本文的核心任务是三件事：

1. **把业务能力切成可独立售卖的产品单元**（不能切太碎，也不能糊成一坨）。
2. **为每个单元找到付费理由**（不是「这个功能很好」，而是「不做会损失什么」）。
3. **排出先后顺序**（资源有限，先做哪个决定了能不能活下来）。

## 1. 映射原则：业务能力 → 产品单元

### 1.1 三条切分标准

一个业务能力要成为**独立产品**，必须同时满足：

| 标准 | 含义 | 反例 |
|---|---|---|
| **有独立买方** | 有人会为它单独批预算 | 「交底审批流」——审批是交底的一部分，不是独立产品 |
| **有独立闭环** | 有输入、有产出、有验收 | 「发明点提炼」单独看是动作，配上检索和权项才是闭环 |
| **有独立价值** | 不做会疼，且疼能换算成钱 | 「术语统一」正确但难卖 |

### 1.2 四种产品形态

对应业务总纲 §9.1：

| 形态 | 卖什么 | 壁垒 | 典型 |
|---|---|---|---|
| **T 工具** | 单点效率 | 低 | 交底表单、年费提醒 |
| **P 平台** | 流程与数据沉淀 | 中（切换成本） | 案件中台、期限引擎 |
| **D 数据** | 检索、监控、预警 | 高（数据资产） | 监控中心、检索库 |
| **X 专家** | 判断与决策 | 高（人 + 经验） | 无效策略、维权比对 |

> **关键判断**：纯 T 型产品没有护城河，但它是**获客入口**。真正赚钱的是 P/D/X。所以产品组合必须是「T 引流 → P 留存 → D/X 变现」。

## 2. 产品全景：四层架构

```
┌─────────────────────────────────────────────────────────────┐
│  L4  决策层                                                   │
│      组合健康诊断 · 估值与交易支持 · 无效/维权策略             │
├─────────────────────────────────────────────────────────────┤
│  L3  数据层                                                   │
│      检索库 · 监控中心 · 期限情报 · 官费与费率库               │
├─────────────────────────────────────────────────────────────┤
│  L2  平台层                                                   │
│      案件中台 · 交接与审批 · 期限引擎 · 商务结算 · Agent 编排  │
├─────────────────────────────────────────────────────────────┤
│  L1  作业层                                                   │
│      交底 · 检索 · 撰写 · 答复 · 年费 · 无效 · 维权 · 国际     │
└─────────────────────────────────────────────────────────────┘
```

### 2.1 每层的商业角色

| 层 | 商业角色 | 客户决策人 | 客单价 | 销售周期 |
|---|---|---|---|---|
| L1 作业 | **获客 + 单点替换** | 部门主管 / IPR | 低 | 短（1–4 周） |
| L2 平台 | **留存 + 扩张** | IP 总监 / IT | 中 | 中（1–3 月） |
| L3 数据 | **持续收费** | IP 总监 / 采购 | 中高（订阅） | 中（1–2 月） |
| L4 决策 | **高毛利 + 品牌** | 法务总 / CFO | 高 | 长（3–6 月） |

> **战略含义**：L1 不能指望赚钱，它的任务是**把客户带进来并产生数据**。L2 是把人留住的锁，L3 是现金流，L4 是利润和壁垒。

### 2.2 规则密度：产品能力的真实地基（数据驱动）

产品切分不能凭感觉。同一个问题——「这个能力值得单独做成产品吗」——可以用业务规则的密度来回答：**规则越多，说明业务复杂度越高，越需要专门的产品承载；规则越少，越应该被合并或作为某产品的一个功能。**

数据来自 `npm run spec:lifecycle`（见 [spec/README.md](spec/README.md)），共 1026 条规则。

| 节点 | 规则数 | 其中决策权 | 复杂度判断 | 产品含义 |
|---|---|---|---|---|
| 00 交底 | 73 | 12 | 高 | 入口产品，用户基数最大 |
| 07 监控 | 66 | 17 | 高 | 独立产品（数据+处置剧本） |
| 10 交接机 | 65 | 17 | 高 | **平台能力，不单卖** |
| 09 PCT | 61 | 11 | 高 | 独立产品（多国规则库） |
| 11 期限引擎 | 60 | 8 | 高 | **平台能力，可模块化出售** |
| 12 商务 | 59 | 16 | 高 | **平台能力，不单卖** |
| 04 答复 | 58 | 9 | 中高 | 独立产品（代理所向） |
| 06 运用 | 58 | 24 | 高 | 独立产品（法务/财务向） |
| 08 布局 | 57 | 16 | 高 | **并入撰写产品**（单独卖太薄） |
| 05 维持 | 56 | 15 | 中高 | 独立产品（现金流最好） |
| 23 终止恢复 | 56 | 7 | 中高 | **并入维持产品** |
| 02 立项 | 55 | 12 | 中高 | 独立产品（决策+预算） |
| 03 撰写 | 54 | 15 | 中高 | 独立产品（代理所主力） |
| 24 诉讼 | 53 | 7 | 中 | 独立产品（低频高价） |
| 01 检索 | 47 | 14 | 中 | 独立产品（与数据源强绑定） |
| 01b FTO | 47 | 12 | 中 | 独立产品（法务向） |
| 13 Agent | 47 | 16 | 中 | **能力层，嵌入各产品** |
| 22 无效 | 42 | 14 | 中 | 独立产品（低频高价） |
| 25 比对表 | 12 | 0 | 低 | **共享对象，不是产品** |

**三条由数据得出的结论**：

1. **决策权密度最高的是 06 运用（24 条）**，远高于其他节点。这印证了「变现环节利益冲突最激烈」——许可、转让、维权都涉及资产处分，每一方都想拍板。**这个产品最难做的不是功能，是权限模型。**

2. **10/11/12 三个横切节点合计 184 条规则，超过任何单个 L1 产品**。这说明平台层不是「胶水」，本身就是一个复杂系统。产品含义：**平台层应该作为独立的模块售卖**（尤其是期限引擎，规则密度高且与行业无关，可以卖给已有系统的企业）。

3. **08 布局（57 条）+ 03 撰写（54 条）= 111 条，是该合并的依据**。两者都服务「保护范围怎么定」这个决策，拆开卖每个都不够厚，合并后是代理所的主力产品。

> **这是一个可复用的判断方法**：规则密度 < 40 的节点不考虑独立产品；40–60 的看买方是否独立；> 60 的通常是平台能力或高价值产品。

## 3. 产品清单

### 3.1 L1 作业层（9 个 SKU）

#### P01 · 交底中心

| 项 | 内容 |
|---|---|
| 覆盖节点 | [00](nodes/00-inventor-disclosure.md) · [00b](nodes/00b-invention-point-chain.md) |
| 形态 | T 工具 → 可升级为 P |
| 目标客户 | 有研发团队的企业（制造业、硬件、材料、软件） |
| 核心场景 | 研发人员在线提报 → AI 结构化 → IPR 按六项与四组事实批准交底 → 交出一份评分建议给立项 |
| 做什么 | 提报门户、结构化引擎、六项技术齐套、权属/署名/奖酬依据/公开时点闭合、一份评分建议 |
| 不做什么 | 不做检索、不做撰写、不做审批流引擎（复用 L2）、不在这里决定要不要申请 |
| 关键产出 | `disclosure_pack`（六项技术齐套，四组事实已定死）+ 一份评分建议。出口只有退回补充、交底完成交下游、终止交底 |
| 定价锚点 | 按提报件数，或按研发人员席位 |
| 壁垒 | **中国法合规三件套**（职务发明、奖酬、宽限期）——通用表单工具做不到 |
| 核心指标 | 齐套一次通过率、交底转化率、撰写返工率 |
| 付费理由 | 「一件专利因为交底不清被驳回，损失的是全部研发投入」 |

> **这是全生命周期最好的入口产品**。原因：用户基数最大（所有研发人员）、痛点最具体（填表痛苦）、合规价值最硬（权属和奖酬是真金白银）。

#### P02 · 检索与可专利性

| 项 | 内容 |
|---|---|
| 覆盖节点 | [01](nodes/01-research.md) |
| 形态 | T + D |
| 目标客户 | 企业 IP 部门、代理所 |
| 核心场景 | 交底完成且初审放行后，为立项提供可专利性证据；要不要申请在 02 |
| 做什么 | 检索式构造、多库聚合、命中可核验、X/Y/A/E 标注、结论绑定 |
| 不做什么 | FTO 已独立为 **P02b**（见下）；不做侵权判定（那是 P08） |
| 关键产出 | `research_report`（7 项齐套） |
| 定价锚点 | 按检索次数 / 按报告份数 |
| 壁垒 | **命中→结论绑定**（不允许「检索一堆但结论无依据」）+ 可核验强制 |
| 核心指标 | 命中可核验率、结论采纳率、检索耗时 |
| 付费理由 | 「一次撞车 = 申请费 + 半年时间 + 机会成本」 |

> **注意**：这个产品和市面上的专利检索工具正面竞争。差异点不在数据量（打不过），而在**结论质量与流程嵌入**——检索完能直接进决策，不用人工搬。

#### P02b · FTO 自由实施

| 项 | 内容 |
|---|---|
| 覆盖节点 | [01b](nodes/01b-fto.md) |
| 形态 | T + X（比对与规避是专家能力） |
| 目标客户 | **企业法务部**（主）、业务部门、投资方（尽调）、代理所/律所 |
| 核心场景 | 产品上市前 / 进入新市场前 / 投融资尽调 / 被诉后补做 |
| 做什么 | 目标市场配置、法律状态过滤、同族折叠、**逐要素 claim chart**、规避设计建议、可举证的结构化报告、保鲜重跑 |
| 不做什么 | 不做可专利性结论（P02）、不做诉讼代理（P08）、不做专利预警（战略层） |
| 关键产出 | `FtoReport`（含检索范围声明、局限声明、逐件结论、复核签署） |
| 定价锚点 | 按项目（单市场/多市场）；持续 FTO 按产品线订阅；重跑按次 |
| 壁垒 | **比对 + 规避 + 可举证报告三件套**。国内检索工具有 FTO 模块，但缺比对工作流与抗辩证据链 |
| 核心指标 | 障碍发现率、规避采纳率、**被诉后报告采信率** |
| 付费理由 | 「不只是防侵权——一份合格的 FTO 报告可阻却**故意**认定，把 1–5 倍惩罚性赔偿压回填平性赔偿」 |

> **为什么必须和 P02 分开卖**：两者问的问题相反（新不新 vs 侵不侵权），买方不同（IP 部门 vs 法务部），预算科目不同，且**混做会同时做错**——FTO 的第一条规则是「只找目标市场内仍然有效的权利要求」，而可专利性检索恰好相反，失效专利仍是现有技术。
>
> **反向风险**：如果做了 FTO 发现障碍仍照常上市，这份报告会变成对方证明「明知故犯」的证据。产品必须提示，这是 FTO 独有的伦理边界。

#### P03 · 撰写与布局

| 项 | 内容 |
|---|---|
| 覆盖节点 | [03](nodes/03-drafting.md) · [08](nodes/08-layout.md) |
| 形态 | T + X |
| 目标客户 | 代理所（主）、企业 IP 部门（次） |
| 核心场景 | 从已批准交底包起草权项树 + 说明书；布局维度检查 |
| 做什么 | 权项树编辑与校验、说明书六段、26.3/26.4 检查、布局五维检查、国别策略 |
| 不做什么 | 不做自动撰写全文（质量不可控）、不做递交（L2） |
| 关键产出 | `draft_claims` + 说明书初稿 + 布局建议 |
| 定价锚点 | 按件（与代理费挂钩） |
| 壁垒 | **发明点 → 权项的翻译质量**（三问法、删除测试、梯度设计） |
| 核心指标 | 返工率、独权数量、首通 OA 次数 |
| 付费理由 | 「权项窄一寸，保护少一片；代理师的产能和 quality 直接决定所的收入」 |

> **买方判断**：这个产品**卖给代理所比卖给企业更容易**。代理所按件收费，工具直接提升产能；企业则容易觉得「这是代理所该干的」。

#### P05 · 年费与权利状态

| 项 | 内容 |
|---|---|
| 覆盖节点 | [05](nodes/05-maintenance.md) · [23](nodes/23-termination-recovery.md) |
| 形态 | P + 服务 |
| 目标客户 | 组合规模 > 100 件的企业 |
| 核心场景 | 年费日程、代缴、宽限期跟踪、终止预警、恢复流程、放弃决策 |
| 做什么 | 多档年费计算、费减、滞纳金、状态机、恢复期限、放弃评分、双人复核 |
| 不做什么 | 不做专利价值评估（L4） |
| 关键产出 | 缴费凭证 + 法律状态 + 组合成本报表 |
| 定价锚点 | **按件年费 + 代缴服务费**（这是最容易变现的模式） |
| 壁垒 | 数据准确性 + 恢复流程的专业性 |
| 核心指标 | 意外终止率（<0.5%）、宽限期补缴率、单件维持成本 |
| 付费理由 | 「一次意外终止，损失 ≥ 十年系统费」 |

> **这是现金流最好的产品**。年费是刚性支出，代缴是天然的服务收入，客户不会因为经济下行就停缴年费（停了就失去权利）。

| 覆盖节点 | [09](nodes/09-pct-international.md) |
| 形态 | P |
| 目标客户 | 出海企业 |
| 核心场景 | 巴黎公约 vs PCT 路径选择 → 国家阶段进入 → 多国期限与费用 |
| 做什么 | 路径测算、30/32 月期限、多国费用矩阵、译文管理、保密审查前置 |
| 不做什么 | 不做各国本地代理 |
| 关键产出 | `PCTFamily` + 多国 docket |
| 定价锚点 | 按国别数 / 按家族 |
| 壁垒 | 多国规则库（更新成本高，一旦建成壁垒极强） |
| 核心指标 | 国家覆盖度、单国成本、进入及时率 |
| 付费理由 | 「错过 30 个月，整个海外市场就没了」 |

---

### 3.2 L2 平台层（4 个能力模块，通常不单独卖）

| 模块 | 覆盖节点 | 规则数 | 作用 | 是否单独售卖 |
|---|---|---|---|---|
| **案件中台** | 全局 | — | 案件主数据、组合视图、Drive | 否（底座） |
| **交接与审批** | [10](nodes/10-handoff-state-machine.md) | 65 | 9 产物键 · 7 态 · 版本与回执 | 否 |
| **期限引擎** | [11](nodes/11-docket-engine.md) | 60 | 法定时钟、升级阶梯 | **是**（规则密度高、与行业无关，可卖给已有系统） |
| **商务结算** | [12](nodes/12-billing-engagement.md) | 59 | 报价/发票/付款、两账分离 | 否 |

> **平台层的产品逻辑**：它通常作为绑定各 L1 工具的底座，价值在于让这些工具共享同一份案件数据和同一套期限；单独出售没有意义，缺了它，各 L1 工具就无法协同。
>
> **但有一个例外**：**期限引擎（60 条规则）可以单独卖**。理由见 §2.2——法定时钟与行业无关、规则密度高、且大量企业已有案件管理系统但没有可靠的期限引擎。这是平台层唯一具备独立售卖条件的能力。

### 3.3 L4 决策层（3 个 SKU）

| SKU | 内容 | 买方 | 定价 | 前提 |
|---|---|---|---|---|
| **P10 组合健康诊断** | 组合结构分析、成本/价值矩阵、放弃建议、布局缺口 | IP 总监 / CFO | 项目制 + 年费 | 需要 ≥3 年数据积累 |
| **P11 估值与交易支持** | 专利估值（成本/市场/收益法）、尽调、交易结构 | 财务 / 投资 / 并购 | 按项目 | 需要交易案例数据 |
| **P12 策略咨询** | 布局策略、无效/维权决策、FRAND 谈判 | 法务总 / 董事会 | 咨询费 | 需要专家 |

> **决策层不是软件，是「软件 + 专家」**。纯软件的决策产品很难卖，因为客户买的是「有人替我担责」。

### 3.4 能力层：Agent 与自动化

对应 [13-agents.md](nodes/13-agents.md)。**Agent 不是产品，是产品的能力**。

| 能力 | 嵌入哪个产品 | 边界 |
|---|---|---|
| 结构化（交底整理） | P01 | 能整理，不能编造 |
| 检索（查询扩展、去噪） | P02、P06 | 能排序，不能下结论 |
| 起草（权项、陈述） | P03、P04 | 能出初稿，不能替人签字 |
| 提醒（期限、异常） | P05、P09 | 能提醒，不能代缴 |
| 比对（claim chart 初稿） | P08 | 能对照，不能判定侵权 |

**产品铁律**：任何 AI 输出必须标注「初稿/建议」，且关键动作（批准、递交、付款、放弃）必须人工确认。**一次 AI 幻觉造成的权利丧失，会毁掉整个产品的信任**。

## 4. 失败模式覆盖矩阵（产品验收）

业务总纲 §10 列了 12 条全局失败模式。**一个产品如果一条都防不住，它就只是一个表单。**

| # | 失败模式 | 主要防线产品 | 次要防线 | 覆盖度 |
|---|---|---|---|---|
| 1 | 公开超 6 个月宽限期 | **P01** | — | ✅ |
| 2 | 交底不清，说明书补不进去 | **P01** | P03 | ✅ |
| 3 | 1.1 编造公开号 | **P01** | P02 | ✅ |
| 4 | 权属不清（离职 1 年内等） | **P01** | — | ✅ |
| 5 | 署名错误 | **P01** | — | ✅ |
| 6 | 涉外未做保密审查 | **P01** | P09 | ✅ |
| 7 | 独权过窄 | **P03** | P02 | ✅ |
| 8 | 忘缴年费终止 | **P05** | — | ✅ |
| 9 | 错过恢复期限 | **P05** | — | ✅ |
| 10 | 无效证据公开日错误 | **P07** | — | ✅ |
| 11 | 官费代理费混账 | **L2 商务** | P05 | ⚠ 需平台 |

## 5. 打包与组合策略

### 5.1 三种打包方式

| 方式 | 内容 | 适合 | 商业目的 |
|---|---|---|---|
| **单品** | 只买一个 SKU | 小客户、试点 | 降低决策门槛 |
| **套装** | 按角色打包（见 5.2） | 中型企业 | 提升客单价 |
| **平台** | L2 + 任选 ≥3 个 L1 | 大型企业 | 锁定 + 数据沉淀 |

### 5.2 按角色的套装

| 套装名 | 包含 | 目标客户 | 逻辑 |
|---|---|---|---|
| **研发提报包** | P01 | 研发驱动型企业 | 一个入口，全员用 |
| **确权包** | P01 + P02 + P03 + P04 | 有 IP 部门的企业 | 从交底到授权全流程 |
| **运营包** | P05 + P06 + P09 | 组合规模大的企业 | 维持 + 监控 + 出海 |
| **攻防包** | P07 + P08 | 诉讼高发行业 | 打与被打 |
| **代理所包** | P02 + P03 + P04 + P07 | 代理机构 | 产能工具 |

### 5.3 打包的禁忌

- **不要把强产品和弱产品硬绑**：客户会认为你在搭售，反而降低对强产品的评价。
- **不要跨角色打包**：研发用的和法务用的不是同一个预算科目，打包会卡在采购。
- **平台不单卖**：平台是「买了三个以上才送」的东西，单卖会拉低感知价值。

## 6. 定价模型

### 6.1 五种模型对比

| 模型 | 适用 | 优点 | 缺点 |
|---|---|---|---|
| **席位制** | P01、P03 | 简单、可预测 | 与价值脱钩，客户会限制席位 |
| **按件制** | P02、P04、P07、P08 | 与业务量挂钩 | 客户会压低件数 |
| **按组合规模** | P05、P06 | 与资产规模挂钩 | 需要准确统计 |
| **订阅 + 用量** | P06、P09 | 收入稳定 + 弹性 | 计费复杂 |
| **服务分成** | 代缴、无效、诉讼 | 零门槛获客 | 收入不稳定 |

### 6.2 定价的底层公式

回到业务总纲 §9.3：

```
可接受价格 ≤ 客户因该失败模式遭受的损失 × 发生概率 × 客户的风险厌恶系数
```

| 产品 | 失败损失 | 发生概率 | 定价带 |
|---|---|---|---|
| P05 年费 | 全部研发投入 | 中（组合大时高） | 高 |
| P01 交底 | 整件专利作废 | 高 | 高 |
| P02 检索 | 申请费 + 半年 | 中 | 中 |
| **P02b FTO** | 被诉赔偿（含 1–5 倍惩罚性）+ 改设计 | 中 | **高** |
| P03 撰写 | 保护价值打折 | 高 | 中 |
| P07 无效 | 索赔全额 | 低 | 高（按案） |
| P08 维权 | 索赔 + 市场 | 低 | 高（按案 + 分成） |

### 6.3 定价的三个陷阱

1. **按「功能数」定价**：客户不关心你有几个功能，只关心里面哪个能救他。
2. **对标竞品定价**：竞品的成本结构和你不同，对标会把毛利压死。
3. **免费试用太久**：专利业务周期长，试用三个月客户还没走完一个案子，无法感知价值。**应该按「一个完整案件」试用，而不是按时间**。

## 7. 客户与采购路径

### 7.1 客户分层

| 层级 | 专利组合规模 | 典型需求 | 主力产品 |
|---|---|---|---|
| **S 小微** | < 50 件 | 别出错、别花冤枉钱 | P01、P05 |
| **M 中型** | 50–500 件 | 流程规范、成本可控 | P01+P02+P03+ 平台 |
| **L 大型** | 500–5000 件 | 组合管理、风险预警 | 全套 + P10 |
| **XL 集团** | > 5000 件 | 全球布局、并购、诉讼 | 全套 + P11+P12 |
| **A 代理所** | — | 产能、质量、交付 | P02+P03+P04+P07 |

### 7.2 采购决策链（这是最容易低估的一环）

```
使用者（IPR / 代理师）  →  提出需求
        ↓
预算人（IP 总监）        →  批预算
        ↓
审批人（CFO / 采购）     →  审价格与合规
        ↓
IT / 安全               →  审部署与数据
```

**每一层的关注点完全不同**：

| 角色 | 关心 | 话术 |
|---|---|---|
| 使用者 | 好不好用、省不省事 | 「少填 60% 的表」 |
| 预算人 | 能不能少花钱、少出事 | 「意外终止率降到 0.5% 以下」 |
| 审批人 | 值不值、能不能砍价 | 「比一次意外终止便宜」 |
| IT | 数据在哪、能不能私有化 | 「支持私有化部署」 |

> **最常见的死法**：只打动使用者，没打动预算人。IPR 觉得好用，但 IP 总监算不出 ROI，预算就过不了。

### 7.4 数据驱动的销售顺序

规则密度（§2.2）不只决定「做什么产品」，也决定「先卖给谁」。按决策权规则密度排序，可以判断客户内部哪个部门最痛：

| 决策权密度 | 节点 | 说明哪个部门最痛 | 首选话术对象 |
|---|---|---|---|
| 最高（24 条） | 06 运用 | 法务、财务、业务三方争夺资产处分权 | **法务总** |
| 17 条 | 07 监控 / 10 交接 | 法务（发函不可逆）、IP 总监（审批链） | 法务总 / IP 总监 |
| 16 条 | 08 布局 / 12 商务 / 13 Agent | IP 总监（预算）、财务（让价）、IT（AI 边界） | IP 总监 |
| 15 条 | 03 撰写 / 05 维持 | 代理师（范围）、IP 总监（放弃决策） | IP 总监 |
| 14 条 | 01 检索 / 22 无效 | IPR（结论）、法务（无效决策） | IP 总监 |
| 12 条 | 00 交底 / 01b FTO / 02 立项 | IPR（齐套）、法务（FTO）、IP 总监（Go） | **IPR（使用者）+ IP 总监（预算）** |

> **执行建议**：先卖 00 交底（使用者最多、决策链最短——IPR 就能推动），用它建立信任；再顺着决策权密度往上卖到法务侧（06/07/22/24），那里客单价高但决策链长。**反向操作（先卖法务侧）通常死在预算审批上**。

### 7.3 采购路径的两个现实约束

1. **国企/上市公司需要合规背书**：GB/T 29490 认证、等保、信创适配。这是硬门槛。
2. **代理所与企业的采购逻辑完全不同**：代理所看产能（人效），企业看风险（少出事）。**不能用同一套销售话术**。

## 8. 交付形态与路线图

### 8.1 交付形态

| 形态 | 适合 | 要求 |
|---|---|---|
| **SaaS 多租户** | 中小客户 | 数据隔离、等保 |
| **私有化部署** | 大型企业、国企 | 容器化、离线授权 |
| **混合** | 大型企业（敏感数据本地） | 数据分级 + 同步 |
| **API / 嵌入式** | 已有系统的企业 | 开放接口、SDK |

**判断依据**：客户的「数据敏感度 × IT 能力」。专利数据本身敏感度中等，但**未公开的申请技术方案**是高度敏感的商业秘密——这一点决定了大型客户几乎必然要求私有化。

### 8.2 路线图：先做什么

**排序依据**（四维打分，1–5）：

| 产品 | 痛点强度 | 付费意愿 | 实现成本（越低分越高） | 数据壁垒 | 总分 |
|---|---|---|---|---|---|
| **P05 年费** | 5 | 5 | 3 | 3 | **16** |
| **P01 交底** | 5 | 4 | 4 | 4 | **17** |
| P02 检索 | 4 | 3 | 2 | 2 | 11 |
| **P02b FTO** | 5 | 5 | 2 | 4 | 16 |
| P03 撰写 | 4 | 4 | 2 | 3 | 13 |
| P06 监控 | 4 | 4 | 2 | 5 | 15 |
| P07 无效 | 5 | 5 | 2 | 4 | 16 |
| P08 维权 | 5 | 5 | 2 | 4 | 16 |
| P09 国际 | 4 | 4 | 2 | 4 | 14 |
| P10 组合诊断 | 4 | 3 | 3 | 5 | 15 |

**结论：先做 P01（交底）+ P05（年费）**，理由：

1. **P01 是入口**：用户基数最大，合规价值最硬，且能自然沉淀「技术资产」数据。
2. **P05 是现金流**：刚性支出，代缴模式最容易变现，且是留存客户的钩子。
3. 两者组合覆盖了 12 条失败模式中的 6 条，形成「最小可用产品集」。
4. 两者都不依赖外部数据源（不像 P02/P06 需要建检索库），**启动成本最低**。

**第二阶段**：P03（撰写）+ 平台层。理由：P03 是代理所的刚需，平台层把 P01/P05 连成一体。

**第三阶段**：P06（监控）+ P09（国际）。理由：需要数据源建设，投入大，但建成后壁垒最高。

**第四阶段**：P07/P08（攻防）+ P10（决策）。理由：客单价高但频次低，适合作为利润产品而非规模产品。

### 8.3 路线图的依赖关系

```
P01 交底 ──┬──► P02 检索 ──► P03 撰写 ──► P04 答复
           │                      │
           └──► P05 年费 ─────────┘
                      │
                      ├──► P06 监控 ──► P07 无效
                      │                    │
                      └──► P09 国际        └──► P08 维权

产品线（与专利轴并行）：
产品方案 ──► P02b FTO ──► 上市 ──► P06 监控
                   │
                   └──► 规避设计 ──► P03 撰写（可能产生新专利点）
                                                  │
                                                  └──► P10 组合诊断
```

**关键依赖**：P01 是所有产品的数据源头（交底包是撰写和检索的输入）。**没有 P01，后面全是空转**。

## 9. 竞争格局与空位

### 9.1 现有玩家（按能力带）

| 玩家类型 | 代表 | 强在哪 | 弱在哪 |
|---|---|---|---|
| **国际平台** | Anaqua、CPA Global、Clarivate | 组合管理、全球期限、数据 | 中国法合规弱、贵、本地化差 |
| **国内检索** | 智慧芽、incoPat、Patentics | 数据量、检索算法 | 流程能力弱、结论不下判断 |
| **国内流程** | 各类案件管理系统 | 便宜、贴合本地 | 只做登记，不做业务逻辑 |
| **代理所自建** | 各大所内部系统 | 贴合业务 | 不外售、不迭代 |
| **通用工具** | 飞书/钉钉 + Excel | 零成本 | 没有业务规则、没有合规 |

### 9.2 空位在哪

三个明确的空位：

1. **中国法合规层**：职务发明、奖酬、宽限期、保密审查、非正常申请——国际产品不做，国内工具不懂。**这是最硬的差异化**。
2. **判断层**：现有产品都停在「记录 + 检索」，没有产品做「发明点提炼、权项梯度、无效胜率、赔偿测算」。**这是从工具升级为专家系统的关键**。
3. **代理所侧产能工具**：国内几乎没有专门给代理所做的产品，代理所还在用 Word + Excel。**这是被忽视的市场**。

### 9.3 不建议正面竞争的地方

| 领域 | 原因 |
|---|---|
| 专利数据量 | 打不过智慧芽/incoPat 的积累 |
| 全球期限管理 | Anaqua 已经做到极致 |
| 通用 OA/审批 | 飞书钉钉免费 |
| 全自动撰写 | 质量不可控，一次事故毁品牌 |

> **战略结论**：不要在「数据广度」上竞争，要在「**法律深度 + 流程嵌入**」上竞争。

## 10. 产品级验收标准

任何产品上线前，必须能回答这 10 个问题。**答不出就不算做完**。

| # | 问题 | 不合格的表现 |
|---|---|---|
| 1 | 它防住了 12 条失败模式中的哪几条？ | 「提升效率」——没说防住什么 |
| 2 | 谁付钱？谁使用？两者是不是同一人？ | 只打动使用者 |
| 3 | 不做这件事，客户最坏损失多少？ | 「行业惯例」——没算过账 |
| 4 | 它的产出物是什么？下游谁消费？ | 只有界面，没有产物 |
| 5 | 它的规则属于法定/程序/商业/质量/数据哪几类？ | 混在一起，不可配置也不可硬编码 |
| 6 | 它涉及哪套时钟？逾期后果是什么？ | 只有一个日期字段 |
| 7 | 它涉及哪个口袋的钱？能否对账？ | 金额是字符串 |
| 8 | 它承载哪个决策点（D1–D7）？决策人是谁？ | 决策退化成一个按钮 |
| 9 | 它的核心指标是什么？健康区间是多少？ | 没有指标 |
| 10 | AI 在里面的边界在哪？哪些必须人工确认？ | AI 直接产出结论 |

## 11. 明确不做的清单

产品逻辑的一半是「不做什么」。

| 不做 | 原因 |
|---|---|
| 全自动撰写申请文件 | 质量不可控，法律风险由客户承担，一次事故毁品牌 |
| 全自动 OA 答复 | 同上 |
| 替代代理所/律所 | 资质限制 + 责任无法承担 |
| 做通用 OA/审批系统 | 正面打不过飞书钉钉 |
| 做专利数据提供商 | 数据积累打不过现有玩家 |
| 做诉讼代理 | 需律师资质 |
| 做官费代收（资金池） | 金融牌照风险 |
| 承诺授权率 | 不可控，且会诱导非正常申请 |

---

## 12. 一页纸总结

| 维度 | 结论 |
|---|---|
| **卖什么** | 不是卖工具，是卖「**少出事**」——用后置的巨额损失给前置的小额投入定价 |
| **先卖谁** | 先卖给**有 IP 部门的中型企业**（有痛点、有预算、决策链短） |
| **先做什么** | P01 交底 + P05 年费（入口 + 现金流，覆盖 6/12 失败模式） |
| **靠什么赢** | 中国法合规深度 + 判断能力（发明点、权项、胜率、赔偿），不拼数据广度 |
| **怎么收钱** | L1 获客（按件）、L2 留存（平台）、L3 现金流（订阅）、L4 利润（项目） |
| **最大风险** | 只打动使用者、打不动预算人；以及 AI 幻觉导致的信任崩塌 |
| **验收标准** | 能答出 §10 的 10 个问题 |
